# 홈페이지 예약 · PMS 판매일보 연동

2026-09-22 구현 기준. 예전 설계 문서보다 이 문서와 실제 API 계약을 우선한다.

## 화면

- `/admin/`: 기존 관리자 로그인, 공지사항 작성·수정·삭제. 예약 관리 링크 추가.
- `/admin/reservations/`: 수분양자·일반 신청 목록, 실제 호실 확인·승인, 반려, 취소, 계정 발급·비밀번호 재발급·비활성화.
- `/owners/`: 발급 ID/PW 로그인, 잔여 박수, 객실 현황·요금 확인, 예약 신청, 본인 내역, 비밀번호 변경.
- `/reservation/book/`, `/reservation/lookup/`: 일반 신청 및 신청 UUID+조회 비밀번호로 조회. 기존 sessionStorage 예약 데모 대신 서버 신청을 사용한다.

메인 홈페이지 예약 버튼의 ‘준비중입니다’ 동작은 이전 오픈 보류 요청에 따라 유지했다. 위 직접 경로에서 개발 화면을 확인할 수 있다. 버튼 공개 및 배포는 사용자가 결정한다.

## 운영 설정 순서

1. 기존 PMS 저장소 `C:\dev\HIO\stayg-pms`의 backend 변경분을 함께 배포한다. 홈페이지만 배포하면 신규 API를 사용할 수 없다.
2. PMS DB에 `backend/.db/patches/20260922-website-booking.sql`, `backend/.db/patches/20260922-website-notices.sql`을 검토 후 적용한다. 전체 스키마 스냅샷도 갱신했다. 개발 중 운영 DB에는 적용하지 않았다. 운영 `DB_SYNCHRONIZE`를 켜지 않는다.
3. PMS 홈페이지 연동 환경변수는 `WEBSITE_PROJECT_ID=7b85fd96-06a0-42f3-bfb9-cbe14c55718a`, `WEBSITE_API_KEY`, `WEBSITE_SESSION_SECRET`을 설정한다. 키는 각각 32자 이상의 별도 무작위 값이다. 기존 PMS DB 등 다른 서비스 설정은 유지한다.
4. Vercel 환경변수는 `PMS_PROJECT_ID`, `PMS_API_KEY`, `ADMIN_PASSWORD_HASH`, `ADMIN_SESSION_SECRET`을 등록한다. 프로젝트 ID는 위 UUID이며 `PMS_API_KEY`는 PMS의 `WEBSITE_API_KEY`와 같아야 한다. PMS 주소 `https://pms-api.hio.ai.kr/api`만 `src/config/website.server.json`에 고정한다. `PMS_API_URL`은 사용하지 않는다. 비밀값에는 `NEXT_PUBLIC_`를 붙이지 않는다.
5. 관리자 로그인 및 공지사항 설정은 [공지 관리자 가이드](./notice-admin-setup.md)를 따른다. 공지는 PMS DB에서 CRUD로 관리하며 저장 즉시 공개한다. Vercel Blob 연결은 필요 없다.
6. PMS의 객실 타입명과 요금표 이름이 다르면 PMS 상수 파일의 `roomTypeMap`에 `{"디럭스 더블 마운틴":"PMS의 실제 타입명"}` 형식으로 연결한다. 잘못된/누락된 매핑은 임의 요금 대신 신청을 차단한다. PMS 객실과 타입을 먼저 등록해야 한다.
7. 관리자 명부에서 계정을 발급한다. 엑셀의 `아이디(호실), 이름, 전화번호, PMS 객실 타입명, 올해 남은 박수` 5열을 헤더 없이 복사·붙여넣어 50행씩 등록할 수 있다. 중복 아이디는 기존 계정·비밀번호·잔액을 바꾸지 않는다. 부분 실패 결과는 화면에 표시한다.

초기 비밀번호는 무작위 8자리이며 발급 응답에서 한 번만 제공한다. 비밀번호 재발급/변경과 계정 비활성화는 기존 세션을 무효화한다. 엑셀의 실제 개인 명부는 아직 제공받지 않았고 임의 계정을 운영 DB에 만들지 않았다.

## 관리자 로그인과 API 배포 확인

관리 메뉴는 로그인 성공 후 표시되고, 로그아웃하거나 세션이 만료되면 숨긴다. `/admin/reservations/` 직접 접근도 서버에서 세션을 확인한다.

로그인 시 `Cannot POST /api/projects/.../website/admin-login-attempt`가 반환되면 홈페이지 요청은 PMS까지 도달했지만 그 서버에 해당 경로가 없는 상태다. 비밀번호 오류와 구분해야 한다. 운영 PMS `GET /api/docs-json`의 `paths`에 `/api/projects/{project_id}/website/...` 경로가 있는지 확인한다. 홈페이지 연동 경로가 전부 없으면 PMS 저장소의 신규 모듈과 `app.module.ts` 등록을 포함한 백엔드 변경분을 먼저 배포해야 한다. DDL 적용이나 홈페이지 재배포만으로 서버 API는 생성되지 않는다.

이번 점검에서는 운영 PMS 공지 API가 `Cannot GET .../website/notices` 404를 반환했고, API 명세에도 website 경로가 없었다. 로컬 PMS에는 컨트롤러와 모듈 등록이 구현되어 있으나 미커밋 변경분으로 남아 있다. PMS 변경분 배포 후 홈페이지 변경분을 배포한다. 연동 키는 Vercel `PMS_API_KEY`와 PMS `WEBSITE_API_KEY`를 일치시키고, PMS `WEBSITE_PROJECT_ID`와 `WEBSITE_SESSION_SECRET`도 설정한다.

홈페이지는 PMS의 라우트 누락 응답을 503과 배포 확인 안내로 바꿔 표시하며, 내부 경로를 그대로 노출하거나 로그인 제한을 우회하지 않는다. HTTP 회귀 검사는 로그인 전 메뉴 숨김·로그인 후 메뉴 표시·로그아웃 후 숨김·보호 페이지 리다이렉트·PMS 경로 누락 시 쿠키 미발급을 포함한다.

## 승인과 금액

신청은 PMS DB의 `website_applications`에만 저장된다. 관리자가 실제 호실을 지정해 승인하면 기존 판매일보 서비스가 각 객실의 예약을 생성한다. 신청 상태·판매일보·수분양자 사용 박수·활동 로그는 하나의 DB 트랜잭션이다. 실패하면 승인되지 않으며 같은 신청 ID로 재시도한다. 승인 상태인 신청을 재승인해도 새 판매일보를 만들지 않는다.

판매일보 채널은 모두 **MB**다. 수분양자는 보유 타입과 동일하면 객실료 0원, 상위 타입은 숙박일별 판매가 차액의 50%, 일반 예약은 요금표 전체 금액을 기록한다. 추가 인원(8세 이상, 객실당 기준 2인 초과)·별도 침구는 각각 1박 22,000원이다. 1~7세는 인원 추가 요금 없이 최대 정원에 포함한다. 세금 10%/쿠폰 15%를 가감하지 않는다. 여러 객실의 금액/인원 분배 합계는 신청 총액/인원과 일치한다.

PMS가 요금을 직접 계산하고 계산 내역을 신청에 보관한다. 브라우저의 금액은 신뢰하지 않는다. 2026~2027년 요일·공휴일 전일을 지원한다. 요금표/공휴일 변경 시 홈페이지 `src/lib/rooms.ts`, `holidays.ts`와 PMS `application/website-booking/pricing.ts`를 함께 갱신하고 대조한다. 홈페이지 요금 확인도 PMS API를 사용하므로 실제 신청·승인 가격은 동일하다.

결제 수단은 유료 건 `현장결제 예정`, 무료 건 `수분양자 무료`다. 요청에 따라 계산 금액을 판매일보 금액에 기입하며 카드 승인·입금 확인은 수행하지 않는다. 실제 현장 수납은 PMS에서 처리한다. 수분양자 요금은 신청 시 계정의 보유 타입을 기준으로 보관한다.

## 단방향 원칙

홈페이지에서 승인/취소할 때만 PMS에 쓰기 작업을 한다. PMS에서 수정·삭제·노쇼 처리해도 홈페이지 상태·요금·사용 박수는 바뀌지 않는다. 판매일보 ID는 JSON으로 보관하고 외래키를 두지 않아 삭제 전파가 없다. 승인 이력 조회는 PMS 실시간 레코드의 존재 여부를 확인하거나 다시 생성하지 않는다. 날짜별 객실 조회는 신규 예약 가능 여부를 위한 읽기 전용 조회다.

관리자가 홈페이지에서 취소할 때에는 남아 있는 해당 출처 판매일보를 취소한다. 이미 삭제된 것은 재생성하지 않는다. 실제 입실·퇴실 기록이 있거나 출처가 바뀐 건은 먼저 PMS에서 운영자가 확인해야 한다. 임의로 해당 데이터를 덮어쓰지 않는다.

## 수분양자 혜택

- 2026년 최대 5박, 이후 매년 15박. 최초 발급 연도는 관리자가 기사용분을 제외한 잔여 박수를 입력한다.
- 예약 승인 때 객실 수×숙박 일수를 할당한다. 잔액은 홈페이지 신청의 할당 기록에서 계산하며 PMS 자료에 의존하지 않는다.
- 비수기 입실 14일 전부터, 하루 1회 신청, 최대 2실·3박. 성수기 7~8월 연 1회·1실·3박. 성수기 운영/업그레이드 확인은 관리자 체크가 필요하다.
- 2026년은 이월하지 않는다. 이후 미사용 연간 부여분의 50%(내림)를 다음 해 3월 31일까지만 사용한다. 이월분을 재이월하지 않는다. 미래 연도 예약에 아직 확정되지 않은 이월분을 쓰지 않는다. 3월~4월 숙박은 3월 31일 밤까지만 이월분 사용이 가능하다.
- 연도/성수기 경계 숙박은 분리 신청을 위해 관리자에게 문의한다. 취소된 성수기 승인 이력은 연 1회 횟수를 자동 복원하지 않는다.
- 취소는 7일 전까지 0%, 정확히 3일 전 50%(내림), 당일·노쇼 100% 차감. 4~6일/1~2일 전은 관리자 입력 없이는 처리하지 않는다. 복원은 아직 유효한 연간/이월분에 한하며 중복 취소로 두 번 복원하지 않는다. 일반 예약의 금전 환불은 현장 처리다.

## 검증 및 남은 운영 작업

PMS 단위/HTTP 테스트는 외부 서비스나 운영 DB 대신 pg-mem DB와 실제 판매일보 서비스를 사용한다. pg-mem은 PostgreSQL의 모든 격리·경합 동작을 재현하지 않으므로, 운영 공개 전 별도 PostgreSQL 검증 DB에서 동시 승인·중간 실패 롤백 검증을 권장한다.

배포 순서는 DDL 적용 → PMS 환경변수 설정 및 백엔드 배포 → Vercel 환경변수 설정 및 홈페이지 배포 → 공지 CRUD·예약 승인 확인이다. 공개 Git 저장소에는 주소·객실 매핑과 빈 `.env.example`만 올리고 실제 인증정보는 올리지 않는다. 이번에 분리한 홈페이지 값은 Git 제외된 `.env.local`, PMS 값은 `backend/.env.website.local`에 보관했다. PMS 보관 파일은 자동 로드되는 설정이 아니므로 배포 환경변수로 옮겨야 한다. 사용자에게 DDL 적용 완료를 확인받았으며, 운영 DB 작업이나 배포는 실행하지 않았다.

2026-09-22 공개 저장소용 환경변수 분리 후 검증: 홈페이지 단위 17개, 공지/예약 프록시 HTTP 검사, PMS 단위 329개·E2E 237개, 키오스크 단위 89개·E2E 46개 통과. 홈페이지/PMS 빌드와 변경 영역 린트도 통과했다. 기존 CMS PostgreSQL 전용 15개는 `CMS_SYNC_TEST_DATABASE_URL`이 없어 자동 제외되었다. 테스트 환경변수를 사용하는 격리 pg-mem PMS 서버에서 공지 조회를 확인하고 종료한 후 전체 검사를 실행했다. 인증 환경변수가 없으면 접근이 거절되는 것도 검증했다. 홈페이지 HTTP 테스트는 테스트 전용 preload로 통신을 로컬 PMS 대역에만 전달하며 운영 API를 호출하지 않는다. 이번에 상수로 넣었던 실제 인증값을 대상으로 로컬 Git 이력(홈페이지 2개·PMS 362개 커밋), 스테이징, 공개 대상 소스와 브라우저 빌드 파일을 검사해 남은 값이 없음을 확인했다. 앞서 홈페이지/PMS의 11개 객실 × 730일 = 8,030개 요금도 일치했다. 재확인 명령은 PMS 빌드 후 `node --experimental-strip-types scripts/verify-pms-rates.mjs`다.
