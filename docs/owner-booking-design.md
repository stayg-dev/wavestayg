# 수분양자 예약 · 최소 구현 설계

> 과거 설계 기록입니다. 최신 [구현·운영 설정](./pms-booking-setup.md)을 우선합니다. 현재는 희망 타입 선택과 보유 타입 기준 차액 계산을 지원하며, 잔액은 홈페이지 신청의 할당 기록에서 계산합니다. PMS 수정·삭제에 따른 역전파는 하지 않습니다.

2026-09-10 개정. [PMS 최소 연동 설계](./pms-integration-design.md)를 따른다. 관리자 확인·승인 화면은 웨이브스테이지 홈페이지에 둔다. 연도 변경·이월 만료는 API 호출 시 자동 반영하고 예외 판단은 관리자가 처리한다. 이번에는 문서만 수정했으며 실제 기능은 아직 구현하지 않았다.

## 1. 이용 흐름

호실·랜덤 비밀번호 로그인 → 날짜·객실 수·인원·투숙객 입력 → 신청 → 홈페이지 관리자 확인·승인 → PMS 예약 등록 성공 → 확정.

신청은 기존 PMS DB의 신청 테이블에 저장하지만 승인 전에는 실제 PMS 예약 목록·판매일보·재고에 반영하지 않는다. 홈페이지의 수분양자 전용 대기 목록에서 반드시 검토한 후 승인해야 한다.

타입·실제 호실은 선택하지 않는다. 본인 계정으로 타인 투숙도 신청할 수 있다. 로그인용 호실은 계정 ID 역할이며 실제 숙박 호실 매핑이 아니다. 홈페이지는 신청 상태와 관리자 처리 기준의 잔여 박수만 보여준다.

결제와 업그레이드 요금 정산은 현장에서 한다. 홈페이지에는 이용 조건·취소 기준·현장 정산 안내를 보여준다. 별도 수분양자 공지는 만들지 않는다.

## 2. 운영 기준

| 항목 | 기준 |
|---|---|
| 무료 박수 | 2027년부터 연 15박, 2026년은 5박 |
| 비수기 | 입실 14일 전부터 신청, 최대 2실·3박 |
| 성수기 | 7~8월, 연 1회·1실·최대 3박 |
| 계산 | 객실 수 × 숙박일 수. 2실 × 3박 = 6박 |
| 동일 타입·업그레이드 | 관리자가 확인·안내, 상위 타입 차액의 50%는 현장 정산 |
| 이월 | 일반 연도 잔여의 최대 50%, 내림, 다음 해 3월 31일까지 |
| 첫해 특례 | 2026년 5박은 12월 31일 소멸, 이월 없음 |
| 취소 | 운영안에 따라 관리자가 복원할 박수 결정. 미정 날짜 구간은 임의 자동 적용하지 않음 |

운영안의 1일 1회 의미, 취소 4~6일 전·1~2일 전 구간, 성수기 예약 오픈·경계 연박·취소 후 횟수 복원은 아직 명확하지 않다. 초기에는 운영자 확인 사항으로 남기고 고객에게 자동 판정 결과를 약속하지 않는다.

## 3. 최소 자동 처리와 수동 처리

자동 처리:
- 필수 입력, 날짜·객실 수·최대 연박·인원 기본 검증.
- 본인 신청만 조회, 중복 제출·중복 확정 차단.
- 일반적인 사용 박수 계산과 홈페이지 승인 후 PMS 등록 성공 시 승인된 박수 차감.
- 관리자 확정·반려·취소 결과 표시.
- 로그인·조회·신청·승인·취소 API에서 연도 변경과 이월 만료를 확인하고 DB 잔여 박수를 갱신.

홈페이지 관리자 처리:
- 수분양자 전용 승인 대기 목록에서 신청 내용 확인. 실제 재고·타입·배정 가능 여부는 기존 PMS 정보를 참고.
- 홈페이지의 “승인 및 PMS 등록”으로 예약 생성. PMS 성공 응답을 받은 뒤 확정 표시.
- 성수기 사용 이력과 예외 확인.
- 취소 시 복원 박수 입력, 현장 비용 안내.
- 최초 계정 등록 시 기존 사용을 반영한 잔액 입력과 예외 조정.
- 비밀번호 재발급 및 잔여 박수 수정.

신청 대기는 잔여 박수를 차감하지 않는다. 승인 시 잔여가 부족하면 확정하지 않고 고객에게 일정·수량 조정을 안내한다. 초과분 자동 유료 전환은 없다. PMS 등록 실패도 확정·차감을 하지 않고 관리자에게 실패 사유와 재시도를 보여준다. 타임아웃이면 같은 신청 ID로 결과를 확인해 중복 등록·차감을 막는다.

## 4. 사용자 DB와 API 호출 시 잔액 갱신

관리자 화면의 기본 항목은 **호실·이름·전화번호·잔여 박수** 네 가지다. 계정 DB는 기존 PMS DB에 둔다. 이름·전화번호는 수분양자 계정의 연락 정보이며, 예약에 입력하는 실제 투숙객 정보와 별개다.

| 필드 | 역할 |
|---|---|
| id, project_id | 계정 식별과 프로젝트 구분 |
| room_number | 로그인용 호실, 프로젝트 안에서 고유. 문자열로 저장 |
| name, phone | 수분양자 이름·전화번호, 전화번호는 문자열로 저장 |
| password_hash | 서버에서 생성한 초기 비밀번호 또는 사용자가 변경한 비밀번호의 해시 |
| active | 계정 사용 여부 |
| benefit_year | 현재 잔액이 계산된 기준 연도 |
| remaining_nights | 해당 연도 신규 부여분의 잔여 박수 |
| carryover_nights | 전년도에서 이월된 잔여 박수 |

잔여 박수 표시는 올해 잔여 + 아직 유효한 이월 잔여의 합계다. 올해분과 이월분은 만료가 달라 DB에서만 구분한다. 이월 만료는 benefit_year의 3월 31일로 고정하여 별도 만료일 필드는 생략한다. 비밀번호 해시와 기준 연도는 관리자 목록에 노출할 필요가 없다. 기존 PMS 활동 로그·계정 메모를 재사용하며 별도 원장·정책 테이블은 만들지 않는다.

신청에는 확정 시 사용한 올해 박수·이월 박수, 원래 혜택 연도·이월 만료일 및 취소 복원 결과를 남긴다. 별도 원장을 만드는 대신 기존 PMS 활동 로그에 관리자 조정 사유를 기록한다.

기존 PMS API 안에 공통 함수 ensureCurrentBenefits(ownerId, now)를 하나 둔다. 인증 성공 후 로그인·내 정보·관리자 목록/상세·신청·승인·취소·잔여 수정에서 필요한 계정에 호출한다. 서버 KST 날짜를 사용하고 브라우저가 기준 연도나 초기화 값을 결정하지 못하게 한다.

1. 트랜잭션에서 계정 행을 잠그고 최신 benefit_year와 잔여를 다시 읽는다.
2. 기준 연도가 지났으면 한 해씩 순서대로 계산한다. 기존 이월분은 재이월하지 않고, 직전 연도 신규 부여분의 잔여에 floor(잔여 × 0.5)를 적용해 새 이월분을 만든다. 2026년분은 이월 0이다.
3. 새 연도 신규 부여분은 15박이며 해당 숙박연도에 이미 확정·차감 기록이 있는 예약 사용분을 빼고 benefit_year를 변경한다. 취소 복원·벌점은 저장된 처리 결과를 반영하며 사용 박수를 다시 차감하지 않는다.
4. 현재 KST 날짜가 4월 1일 이후이면 현재 연도 carryover_nights를 0으로 만든다.
5. 실제 변경이 있을 때만 DB에 저장한다. 승인·취소에서는 연도 갱신과 예약·잔액 처리를 같은 트랜잭션으로 완료한다.

예: 2027년 신규 부여분 잔여 7박 → 2028년 1월 첫 API 호출 시 신규 15박 + 이월 3박 = 18박. 4월 1일 이후 미사용 이월분은 소멸한다. 2026년 잔여가 있어도 2027년에는 이월 없이 15박이다. 몇 년 동안 접속하지 않았더라도 각 연도 순서로 계산하되 지난 연도의 15박을 모두 더하지 않는다. 비활성 계정의 미접속 기간 혜택을 새로 부여하는 처리는 자동 실행하지 않고 재활성화 시 관리자 확인을 거친다.

스케줄러는 필요 없다. 1월 1일 자정에 모든 DB 행이 즉시 바뀌는 방식이 아니라 해당 계정을 처음 읽거나 처리하는 API에서 갱신된다. 관리자 목록·상세도 갱신 후 값을 반환하므로 화면에는 지난 연도 잔액이 남지 않는다. 인증 없는 요청이나 잘못된 비밀번호 시도는 잔액 변경을 유발하지 않는다.

실제 숙박일에 유효하고 먼저 만료되는 이월분부터 차감한다. 3월에 4월 숙박을 신청해도 이월분을 사용하지 않는다. 3월 31일 체크인·4월 1일 체크아웃의 1박은 3월 31일 숙박으로 판단한다.

미래 연도 예약을 승인할 때는 계정의 benefit_year를 미래로 먼저 옮기지 않는다. 기존 신청 데이터에 숙박연도별 승인 사용 박수를 저장하고 해당 연도 기본 한도에서 이미 승인한 사용분을 뺀 범위를 검증한다. 아직 정산되지 않은 미래 이월분은 선사용하지 않는다. 실제 연도가 바뀌면 그 사용분을 반영해 계정 잔액을 만든다. 초기 연말 경계 예약은 관리자에게 숙박연도별로 나눠 처리하도록 안내한다. 새 테이블은 추가하지 않는다.

2026년 잔액은 실제 기존 사용을 뺀 5박 이내로 가져오고 계정 재발급으로 재충전하지 않는다. 2026년분은 다음 연도로 이월하지 않는다. 전년도 이월분을 다시 이월하지 않는다.

관리자 입력값도 음수·기존 사용량을 넘는 복원·중복 복원을 서버에서 거절한다. 신청 버전·PMS 예약 생성·계정 잔여 변경을 PMS DB의 같은 트랜잭션으로 저장하여 두 관리자가 동시에 잔여를 덮어쓰지 않게 한다. 연도 갱신도 같은 계정 잠금을 사용해 동시 로그인이나 승인으로 15박을 중복 지급하지 않는다. 화면은 홈페이지에 두고 이 처리는 기존 PMS 백엔드가 수행한다.

### 비밀번호 발급·변경

- 관리자가 호실 목록을 등록하면 서버가 호실별 계정과 **8자리 랜덤 초기 비밀번호**를 자동 생성한다. 호실을 로그인 ID로 사용하며 영문 대소문자·숫자 조합의 암호학적 난수로 생성한다. 호실·이름·전화번호에서 비밀번호를 유도하지 않는다.
- 같은 프로젝트의 이미 등록된 호실은 중복 계정을 생성하거나 비밀번호·잔여 박수를 덮어쓰지 않고 등록 결과에 표시한다. 재발급은 별도 관리자 동작으로만 처리한다.
- 최초 자동 생성은 호실만으로 가능하다. 이름·전화번호는 미입력 상태로 두고 이후 계정 편집에서 입력하며 가짜 값을 채우지 않는다. 기존 계정을 가져오는 경우 잔여 박수는 실제 사용 내역을 반영한다.
- 생성 직후 관리자에게 한 번 표시하여 사용자에게 전달한다. 평문은 DB·로그·일반 계정 조회 응답에 남기지 않고 password_hash만 저장한다. 자동 문자 발송은 추가하지 않는다.
- 사용자는 로그인 후 /owners/account에서 현재 비밀번호·새 비밀번호·새 비밀번호 확인을 입력해 변경한다. 최초 로그인 때 변경 안내를 보여주되 강제 변경 절차는 추가하지 않는다.
- POST /api/owners/password는 로그인 계정과 현재 비밀번호를 검증하고 새 해시로 교체한다. 화면의 계정 ID나 호실을 신뢰해 다른 사용자 비밀번호를 바꾸지 못하게 한다. 변경 요청에는 기존 세션·Origin 검증을 적용한다.
- 변경 또는 관리자 재발급 후에는 기존 세션을 무효화하고 새 비밀번호로 다시 로그인하게 한다. 세션은 현재 password_hash에 연결하여 검증하는 방식으로 별도 세션 테이블 없이 처리할 수 있다.
- 분실 시 홈페이지 관리자가 본인 확인 후 새 8자리 랜덤 비밀번호를 재발급한다. 기존 비밀번호 조회와 전화번호만 입력하는 자동 재설정은 제공하지 않는다. 초기 발급·재발급의 8자리 규칙을 사용자가 변경하는 비밀번호의 고정 길이로 강제하지 않는다.
- 비밀번호 변경·재발급은 계정의 이름·전화번호·예약·잔여 박수에 영향을 주지 않는다. 활동 로그에는 처리 사실과 주체만 남긴다.

## 5. 취소는 관리자 승인

대기 신청 철회는 벌점 없이 처리한다. 확정 예약은 최초 취소 요청 시각을 기록하고 홈페이지 관리자가 취소 요청을 별도로 확인한다. 홈페이지에서 취소 처리하면 기존 PMS 취소와 무료 박수 복원을 함께 수행하고 성공 후 취소 완료로 표시한다. 실패·응답 유실은 조회 후 같은 요청으로 재시도한다.

운영안: 7일 전 무료, 3일 전 50% 차감(내림), 당일·노쇼 100% 차감. 3박의 50% 차감은 벌점 1박·복원 2박이다. 누락된 구간은 관리자가 운영 기준을 확인한 뒤 처리한다.

복원은 신청에 남긴 원래 부여 연도·만료일 범위로 제한한다. 만료된 박수를 올해 사용 가능한 박수로 되살리지 않는다. 연도 갱신 이후에 처리하는 이전 연도 취소가 이월액에 영향을 주면 관리자 수동 조정으로 근거와 처리 결과를 기록한다. 미래 연도 취소는 해당 신청의 연도별 사용 기록을 정정하며 올해 잔액에 더하지 않는다. 노쇼는 사용 박수를 유지하고 같은 박수를 추가 차감하지 않는다. 성수기 횟수 복원 여부도 관리자 확인 사항이다.

홈페이지에는 자동 환불 계산 화면 대신 “취소 요청 후 관리자가 혜택 복원과 현장 정산 사항을 안내합니다”라고 표시한다. 실제 취소 완료와 처리 후 잔액은 조회 화면에서 확인할 수 있다.

## 6. 첫 버전 화면·검증

이용자 화면은 로그인, 내 신청 목록·잔여, 신청 폼, 상세·철회/취소 요청, 내 계정의 비밀번호 변경으로 구성한다.

관리자 화면은 기존 /admin 로그인과 메뉴를 확장한다.
- /admin/reservations: 일반 예약 전용 목록. 수분양자와 공통 승인·취소 서비스를 쓰지만 무료 박수 처리는 적용하지 않는다. [일반 예약 설계](./general-booking-design.md)를 따른다.
- /admin/owner-reservations: 수분양자 전용 대기 목록·상세·승인·반려·취소 요청 처리.
- /admin/owners: 호실·이름·전화번호·잔여 박수 목록, 계정 편집·비밀번호 재발급. 이월 내역은 필요할 때만 상세 표시.
- 기존 공지 관리: 그대로 유지.

대기 건수·접수 시각·입실일을 표시하고 승인 대기를 기본으로 보여준다. 일반 예약과 섞지 않는다. 열람만으로 처리 완료되지 않으며, 연동 실패·결과 확인 필요 건도 처리할 목록에 계속 남긴다. 상세에는 승인 시각·최근 연동 오류·PMS 예약번호와 재시도를 제공한다. 반려 사유는 이용자에게 보여줄 내용과 내부 메모를 구분한다.

PMS에는 새 검토 화면을 만들지 않고 승인 완료된 실제 예약만 기존 화면에서 관리한다. 독립 대시보드·통계·알림 센터·작업 큐는 만들지 않는다.

필수 검증은 본인·관리자 접근 제한, 수분양자 전용 대기 목록, 2실 × 3박 계산, 승인 전 PMS 예약·차감 없음, 승인 연동의 전체 성공/롤백, 응답 유실 재시도와 중복 확정·복원 차단, 2026년 이월 제외, 연도 변경 동시 호출·여러 해 미접속, 3월 31일/4월 1일 경계, 다음 연도 승인분 중복 지급 방지에 집중한다. 상세 구현 시 해당 저장소의 필수 검증 규칙을 따른다.
