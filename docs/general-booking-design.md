# 홈페이지 일반 예약 · 관리자 확인 설계

> 과거 설계 기록입니다. 최신 [구현·운영 설정](./pms-booking-setup.md)을 우선합니다. 현재 조회는 신청 UUID+비밀번호 방식이며, 변경/취소는 홈페이지 관리자가 처리합니다. PMS 수정·삭제에 따른 역전파는 하지 않습니다.

2026-09-11 초안. 일반 예약도 수분양자 예약처럼 **홈페이지에서 관리자가 확인·승인**한다. 이번 변경은 설계 문서이며 현재 예약 데모나 관리자 기능을 구현한 것은 아니다. [공통 PMS 연동 설계](./pms-integration-design.md)를 따른다.

## 1. 접수와 확정을 구분한다

고객 신청 → 접수번호 발급·확인 대기 → 홈페이지 관리자 검토 → 승인 및 PMS 등록 → 등록 성공 후 예약 확정.

신청은 기존 PMS DB의 공통 신청 테이블에 저장한다. 승인 전에는 실제 PMS 예약·판매일보·재고에 반영하지 않는다. 접수번호는 신청을 식별하는 번호이며 객실 확보나 예약 확정을 뜻하지 않는다.

일반 예약과 수분양자 예약은 접수·승인·반려·취소·PMS 연동 처리를 재사용한다. 일반 예약에는 수분양자 계정과 무료 박수 처리를 적용하지 않는다. 결제는 기존 최소 설계에 따라 현장에서 정산한다.

## 2. 고객 화면

| 화면 | 처리 |
|---|---|
| `/reservation/book/` | 날짜·객실 수·성인/아동·예약자·실제 투숙객·전화번호·요청사항·이용 안내 확인 후 신청 |
| 접수 완료 | 접수번호와 조회 방법, 신청 내용, ‘관리자 확인 후 확정됩니다’ 표시 |
| `/reservation/lookup/` | 본인 인증 후 접수·확정·반려·취소 요청 상태와 고객 안내 사유 조회 |
| 대기 신청 상세 | 신청 철회 가능. 승인 처리와 경합하면 서버 최신 결과를 표시 |
| 확정 예약 상세 | 확정된 일정·수량·타입·요금 확인 및 취소 요청 |

초안에서는 일반 고객이 현재 홈페이지처럼 **희망 객실 타입을 선택**한다. 선택은 확정 배정이 아니며 최종 제공 가능 여부를 관리자가 확인한다. 수분양자는 기존처럼 타입을 선택하지 않는다. 일반 고객의 타입 선택 유지 여부는 운영자 확인 항목이며, 실제 호실은 두 유형 모두 고객이 선택하지 않는다.

비회원 신청을 기본으로 한다. 접수번호와 고객이 설정한 조회 비밀번호로 인증하고, 서버는 비밀번호 해시만 저장한다. 인증 후 해당 신청에만 접근하는 만료 있는 보호된 세션 쿠키를 발급한다. 번호·이름·전화번호만으로 개인정보를 조회하지 않는다. 번호와 비밀번호는 URL에 넣지 않는다. 시도 제한·Origin 검사 등 기존 인증 보호를 재사용한다. 분실 시 운영자가 본인 확인 후 조회 비밀번호를 재발급하며 이전 조회 세션은 무효화한다.

화면에 표시하는 요금은 운영 요금이 연결되기 전까지 예약 가격으로 약속하지 않는다. 현재 Figma의 58,000원, 세금 10%, 할인 코드, 예약 가능 표시를 실제 요금·세율·재고 규칙으로 사용하지 않는다. 요금표가 연결되면 서버가 계산한 예상 금액과 안내 기준을 신청 시 저장한다. 아직 연결되지 않았다면 ‘요금은 관리자 확인 후 안내’로 표시한다.

## 3. 홈페이지 관리자

기존 `/admin` 인증과 레이아웃에 **공지 / 일반 예약 / 수분양자 예약 / 수분양자 계정** 메뉴를 둔다.

- `/admin/reservations`: 일반 신청만 조회한다. 기본 탭은 확인 대기이며 확정·반려·취소 요청·취소 완료로 조회할 수 있다.
- `/admin/owner-reservations`: 수분양자 전용 목록을 유지한다.
- 두 목록에서 미처리 건수·취소 요청·연동 결과 확인 필요 건을 표시한다. 신청 유형은 서버가 구분하며 일반 예약을 수분양자 목록에 섞지 않는다.
- 일반 목록의 기본 정보는 접수번호·접수 시각·입실/퇴실·객실 수·인원·예약자·연락처·신청 상태다. 희망 타입을 받는 경우 함께 표시한다.
- 상세에서 원래 신청 내용, PMS 배정 가능 여부, 확정할 조건과 요금, 고객에게 보여줄 안내, 내부 메모를 확인한다.

관리자가 신청을 열어 보는 것만으로 처리 완료가 되지 않는다. **승인 및 PMS 등록** 또는 **반려**를 명시적으로 실행해야 한다. 처리자·시각·사유를 기존 PMS 활동 로그에 남긴다. 공용 관리자 로그인에서는 개별 직원 신원을 확인했다고 기록하지 않는다.

## 4. 승인과 조건 변경

1. 관리자가 기존 PMS 정보를 보고 해당 날짜의 타입·수량·인원 수용과 요금을 확인한다.
2. 신청과 다른 날짜·타입·수량·요금이 필요하면 고객에게 연락해 동의를 받은 뒤 변경 조건과 안내 이력을 기록한다. 원래 신청 내용은 유지한다. 연락만 했거나 고객 응답이 없으면 대기 상태로 둔다.
3. 홈페이지에서 확정할 조건을 확인하고 ‘승인 및 PMS 등록’을 실행한다.
4. PMS 백엔드는 최신 신청 상태·버전·프로젝트 권한과 기존 PMS 예약 조건을 다시 검사한다. 연결된 PMS 예약 생성과 신청 확정을 같은 트랜잭션으로 처리한다. 여러 객실이면 모두 성공하거나 모두 롤백한다.
5. 성공 응답 후에만 고객 화면에 ‘예약 확정’, 확정 조건·금액·PMS 예약번호를 표시한다. 일반 예약이므로 혜택 잔여는 변경하지 않는다.

최초 버전은 기존 전화·문자로 안내하고 안내 사실을 메모한다. 자동 발송 성공을 약속하지 않는다. 관리자 확인 전후에 재고가 바뀌면 기존 PMS 검증 결과에 따라 승인을 거절하고 재검토한다. 홈페이지의 별도 재고 확보·대기 재고 테이블은 만들지 않는다.

## 5. 상태와 취소

| 상태 | 고객 의미 | 관리자 처리 |
|---|---|---|
| `pending` 확인 대기 | 접수 완료, 미확정 | 승인 또는 반려 |
| `confirmed` 확정 | PMS 등록 성공 | 취소 요청 검토 |
| `rejected` 반려 | 예약 제공 불가 | 고객 안내 사유 보관 |
| `withdrawn` 신청 철회 | 승인 전 고객 철회 | PMS 취소 불필요 |
| `cancel_requested` 취소 요청 | 요청 접수, 아직 취소 미완료 | PMS 취소 처리 |
| `cancelled` 취소 완료 | PMS 취소 성공 | 처리 결과 보관 |

대기 신청 철회는 PMS 예약을 만들지 않는다. 확정 예약은 최초 취소 요청 시각을 보관하고, 홈페이지에서 관리자가 취소 조건과 현장 정산 사항을 확인한다. PMS 취소 성공 후에만 취소 완료로 표시한다. 취소 요청만으로 재고를 풀지 않는다. 취소를 진행하지 않는 경우에도 고객에게 사유를 안내하고 처리 이력을 남긴다.

고객이 취소 요청을 철회해 기존 예약을 유지하기로 한 경우, 관리자가 합의 기록을 남기고 `confirmed`로 되돌린다. PMS 취소 처리 중이거나 결과가 불명확하면 상태를 먼저 되돌리지 않는다. 이전 취소 요청 시각과 처리 결과는 기존 활동 로그에 보존한다.

일반 고객의 취소 기준은 별도로 확정한다. 수분양자의 무료 박수 복원 규칙이나 현재 데모의 ‘3일 전 무료 취소’를 일반 예약에 자동 적용하지 않는다. 승인 전부터 고객에게 실제 적용할 이용·취소 안내를 보여주고 확인한 내용을 신청에 보관한다.

## 6. 기존 데이터와 API 확장

새 예약 DB나 신청 테이블을 유형별로 따로 만들지 않는다. 기존 공통 신청 설계에 일반 예약용 필드만 보완한다.

| 구분 | 내용 |
|---|---|
| 식별 | 신청 ID·접수번호·프로젝트·`source=general`·접수 시각·중복 제출 키 |
| 원래 신청 | 날짜·수량·성인/아동·예약자/투숙객·연락처·희망 조건·고객 요청 |
| 조회 | 일반 조회 비밀번호 해시. 관리자 목록·일반 응답에 해시를 노출하지 않음 |
| 안내와 요금 | 신청 당시 안내 내용/버전·확인 시각·예상 금액(있을 때), 승인 조건·확정 총액·고객 합의 기록 |
| 처리 | 상태·버전·처리 주체/시각·최초 취소 요청 시각·고객 안내 사유·내부 메모·연결 PMS 예약 ID 목록·최근 연동 오류 |

홈페이지의 논리 API는 신청, 조회 인증, 본인 상세, 철회, 취소 요청이다. 관리자 목록·상세·승인·반려·취소 처리는 수분양자와 공통 서비스를 사용하고 유형별 권한·검증만 나눈다. 실제 PMS 경로와 필드 매핑은 PMS 저장소를 확인한 뒤 확정한다. 현재 데모의 숫자 인덱스를 PMS 타입 ID로 바로 사용하지 않는다.

일반 신청 API가 신청 유형을 직접 `general`로 지정한다. 고객이 제출한 `source`, 수분양자 계정 ID, 상태, 확정 금액, 프로젝트 권한을 신뢰하지 않는다. PMS 접속 자격증명은 Next.js 서버에만 둔다.

승인·취소는 같은 신청 ID와 작업 구분을 사용해 중복 처리를 방지한다. 응답 유실이면 신청/PMS의 기존 결과를 조회한다. 실패가 확인되면 같은 신청으로 재시도하고, 결과를 알 수 없으면 관리자 목록에 ‘연동 결과 확인 필요’를 표시한다. 결과가 불명확한 동안 새 예약 생성·반려·철회 같은 충돌 작업으로 우회하지 않는다. 확정·실패를 추정하거나 신청을 목록에서 없애지 않는다.

PMS에서 직접 변경된 예약은 상세 조회 시 연결 상태를 확인하고 관리자 확인 대상으로 표시한다. 일반 예약도 홈페이지 취소 처리를 기본으로 하며 별도 양방향 동기화 엔진은 추가하지 않는다.

## 7. 구현 순서와 확인 사항

1. 일반·수분양자 공통 신청 모델, 상태 전이, 관리자 권한과 PMS 승인/취소 서비스.
2. 홈페이지 관리자 일반 예약 목록·상세·승인·반려·취소 처리와 유형별 목록 구분.
3. 고객 신청·접수 완료·안전한 비회원 조회·철회/취소 요청.
4. 현재 데모의 결제 단계·즉시 확정·가상 예약 가능 수·발송 완료 문구 교체.

검증은 승인 전 PMS 예약 없음, 유형별 목록·권한 분리, 승인 후에만 확정, 다실 전체 롤백, 응답 유실 후 중복 등록 방지, 승인과 철회의 경합, 취소 성공 전 재고 유지, 비회원의 다른 신청 조회 차단에 집중한다.

운영 확정이 필요한 항목: 일반 고객의 희망 타입 선택 여부, 운영 요금과 추가 인원 요금의 출처, 객실 수·최대 숙박일 제한, 일반 취소 기준, 고객 문의 대응 시간. PMS의 실제 필수 등록값·미배정 예약 지원·중복 검사 범위도 구현 전에 확인한다.
