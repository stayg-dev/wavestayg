# 홈페이지 요금·할인·방막기 관리

2026-10-13 · 로컬 구현 및 검증 문서. 운영 DB 적용과 배포는 사용자가 수행한다.

## 구현 범위

`/admin/settings/`에서 홈페이지 예약 접수, 객실 기본 요금, 날짜별 요금·할인, 방막기, 부가서비스 요금과 변경 이력을 관리한다. 예약 관리·공지사항 관리 화면에 진입 링크를 추가했다. 기존 관리자 인증을 재사용하며 **모든 영속 데이터는 기존 PMS PostgreSQL DB에 저장한다.** Next.js는 화면과 인증된 프록시만 담당한다.

NICEPAY 결제는 후속 단계다. 현재 신청은 기존과 같이 PMS 예약 등록 및 현장 정산 흐름을 사용한다. [NICEPAY 설계](./nicepay-integration-design.md)의 주문·재고 확보·승인·환불은 이번 구현에 포함하지 않는다.

## 요금과 별도 할인 필드

각 객실 타입의 주중·금요일·토요일/공휴일 전일 요금과 날짜별 특가에 다음 값을 저장한다.

| API 필드 | PMS 내부 필드 | 의미 |
|---|---|---|
| `base_amount` | `baseAmount` | 정상가, 객실 1실·1박 원화 정수 |
| `discount_amount` | `discountAmount` | 별도로 입력하는 정액 할인액, 0원은 할인 없음 |
| `sale_amount` | `saleAmount` | 서버가 정상가 − 할인액으로 계산하는 실제 판매가 |

관리자는 정상가와 할인액을 입력한다. 실제 판매가는 읽기 전용 계산 결과다. 브라우저가 보낸 판매가를 신뢰하지 않고 PMS가 다시 계산한다. 정상가는 1~10,000,000원, 할인액은 0원 이상·정상가 미만의 정수여야 한다. 무료 수분양자 혜택은 이 가격에 별도로 적용하며 일반 판매가를 0원으로 저장하지 않는다.

예: 정상가 65,000원, 할인액 5,000원 → 판매가 60,000원. 할인은 조회·신청 시 다시 차감하지 않는다. 2실·2박이라면 각 숙박일의 할인 적용 판매가에 객실 수를 곱해 합산한다. 날짜별 특가는 기본 요금 전체를 대체하며 기본 요금의 할인과 중복 적용하지 않는다.

기간 일괄 편집에서 객실 타입, 첫/마지막 숙박일, 요일을 선택해 정상가·할인액을 지정하거나 날짜 특가를 해제한다. `할인액 5,000원 입력` 버튼을 제공한다. 먼저 객실 기본 요금을 설정해야 날짜별 특가를 저장할 수 있다.

인원·침구 추가 요금은 일반/수분양자별로 PMS에 저장하고 매박 적용한다. 얼리·레이트 시간당 요금도 표시 설정에 포함한다. 이 서비스는 기존과 같이 프런트에서 요청하며 예약 폼에서 자동 청구하지 않는다. 무료 연령과 객실 정원·수분양자 혜택 규칙은 기존 정책을 유지한다.

## 판매와 재고

판매 판단은 전체 접수 허용 → 일반/수분양자 허용 → 모든 숙박일의 타입별 방막기 → 요금 유효 기간 및 설정 → 실제 PMS 재고 순서다. 하나라도 불가하면 신규 신청을 거절한다. 클라이언트 버튼을 우회한 API 요청과 관리자 홈페이지 전화 예약도 같은 규칙을 적용한다.

- 전체 접수 중지와 일반/수분양자별 중지를 각각 설정할 수 있다.
- 방막기는 PMS 객실 타입 ID·숙박일·대상(`all`, `general`, `owner`)·내부 사유로 저장한다.
- 마지막 숙박일은 포함하며 퇴실일은 제외한다. 연박 중 하루라도 막히면 신청할 수 없다.
- 방막기 해제는 선택한 대상만 해제한다. 다른 대상의 차단, 전체 중지, 요금 미설정, 재고 부족은 유지된다.
- 방막기로 기존 예약을 취소하거나 가짜 예약/판매일보를 생성하지 않는다. 기존 예약 금액도 유지한다.
- 특정 호실 사용 불가는 PMS의 기존 객실 운영 설정을 사용한다. 이번 방막기는 홈페이지의 타입별 판매 중지다.
- 관리자 `DB만 등록`/이미 차감된 과거 내역은 기존 자료 정리 경로로 유지한다. 신규 객실 재고를 판매하지 않으므로 현재 방막기와 판매 요금을 적용하지 않고 기존 기록용 계산을 사용한다.

## PMS DB 구조

기존 공지 카탈로그와 같은 프로젝트 단위 집합 저장 방식을 채택했다. 별도 날짜별 테이블 대신 제한된 크기의 JSONB 설정을 원자적으로 저장한다.

| 테이블 | 내용 |
|---|---|
| `website_sales_catalogs` | 프로젝트 유일 행, UUID 버전, 접수 스위치, 안내, 유효기간, 타입별 기본 요금, 날짜별 요금·할인, 방막기, 서비스 단가 |
| `website_sales_changes` | 프로젝트·요청 UUID 유일, 요청 해시, 새 버전, 변경 사유, 변경 전후 전체 설정, 시각 |
| 기존 `activity_logs` | 홈페이지 관리자에 의한 요금·판매 설정 변경 요약과 상세 이력 참조 |

신규 설정 저장과 신규 예약은 같은 프로젝트 카탈로그 행을 먼저 잠근다. 변경 이력·활동 로그는 설정과 같은 트랜잭션에 기록한다. 동일 요청 번호/동일 내용의 재요청은 기존 결과를 반환하고, 다른 내용은 409로 거절한다. 저장 버전이 다르면 덮어쓰지 않고 새로고침을 요구한다. 신규 예약은 제출된 견적 버전과 현재 버전이 다를 때 재확인을 요구한다.

프로젝트의 실제 PMS 타입 ID만 저장할 수 있다. 타입 이름은 서버가 정규화하고 타입 매핑은 기존 홈페이지 예약 대상 11개 타입을 따른다. 공용 관리자 인증으로 개별 직원 이름을 추정하지 않고 `홈페이지 관리자`로 기록한다.

제한: 기본 요금 최대 100타입, 날짜 특가·방막기 각각 10,000건, 설정 JSON 최대 2.5MB, 설정 유효 기간 최대 1,096일. UI 일괄 선택 최대 366일, 공개 조회 최대 31일. 공휴일 전일 계산은 현재 등록된 2026~2027년 달력을 사용하므로 이후 연도와 임시 공휴일은 날짜 특가로 설정하거나 달력을 갱신해야 한다.

## API와 화면 연결

| 홈페이지 API | 용도 |
|---|---|
| `GET /api/pms/admin/sales/` | 설정·버전·PMS 객실 타입 조회 |
| `POST /api/pms/admin/sales/` | `config`, `revision`, `request_id`, `reason`으로 전체 설정 저장 |
| `GET /api/pms/admin/sales/history/` | 최근 30건 변경 전후 이력 |
| `GET /api/pms/sales/?from=YYYY-MM-DD&to=YYYY-MM-DD` | 공개 날짜별 정상가·할인액·판매가·접수 상태 |
| `GET /api/pms/owner-inventory/` | 로그인한 수분양자 대상 재고 조회 |

PMS 경로는 `/api/projects/:project_id/website/...`이다. 프록시가 관리자 세션, 쓰기 same-origin, 요청 크기를 검사한다. PMS는 기존 서버 전용 키와 프로젝트 범위를 검사한다. 공개 응답에는 내부 방막기 사유나 감사 이력을 내보내지 않는다.

2026-10-14 표시 범위 변경: 객실 안내·상세 및 수분양자 페이지의 요금 안내는 기존 정적 요금표로 복원했다. 비수기·준성수기·성수기(피크 포함) 탭을 제공하고 비수기에는 기존 5,000원 할인 및 취소선 → 할인 금액을 표시한다. 부가서비스 안내도 기존 정적 단가를 사용하며, 안내 표시는 관리자 판매 설정이나 PMS 조회 상태와 무관하다.

실제 일반 예약 화면의 금액, 서버 견적·결제 및 예약 접수 검증은 계속 PMS 설정을 사용한다. 정적 안내 금액은 예약 계산의 대체값으로 사용하지 않는다. 관리자 금액 설정과 최초 설정용 비수기 초기값 기능도 유지한다.

## 운영 반영 순서

1. 기존 PMS DB를 백업하고 `C:/dev/HIO/stayg-pms/backend/.db/patches/20261013_website_sales.sql`을 적용한다. 스키마 스냅샷도 갱신했다. 로컬 작업 중 운영 DB에 적용하지 않았다.
2. PMS 백엔드를 먼저 배포하고 홈페이지를 배포한다. 기존 PMS 연결 설정과 홈페이지 관리자 인증을 재사용한다.
3. `/admin/settings/` 최초 설정 시 기존 금액표(`seasonal-rate-table.ts`)의 비수기 정상가와 별도 할인액 5,000원을 초안으로 채운다. 주중/금요일/토요일 정상가는 스탠다드 55,000/75,000/95,000원, 디럭스 65,000/85,000/105,000원, 주니어 75,000/95,000/115,000원, 프리미엄·로프트 더블/트윈 85,000/105,000/125,000원, 로프트 패밀리 95,000/115,000/135,000원이다. 저장 이력이 있거나 기본 요금이 있으면 자동으로 변경하지 않는다. `미설정 객실에 금액표 초기값 채우기`로 비어 있는 객실만 채울 수도 있다. 성수기 요금은 날짜별 설정으로 별도 입력한다. 유효기간·서비스 단가 등을 확인하고 변경 사유와 함께 저장해야 PMS에 반영되며, 초기값을 채우는 것만으로 예약 접수를 활성화하지 않는다.
4. 날짜별 특가·방막기를 설정하고 접수 허용을 저장한다. 초기 설정이 없으면 접수는 중지된다. 이 전환은 일반·수분양자 모두에 적용되므로 운영자가 요금 입력과 활성화를 같은 점검 시간에 진행해야 한다.
5. 공개 요금, 일반/수분양자 견적, 신규 접수, 방막기 및 재개, 기존 예약 조회를 확인한다. 실제 배포는 사용자가 수행한다.

검증은 운영 DB와 분리된 메모리 PostgreSQL 호환 테스트 저장소 및 로컬 HTTP 서버를 사용한다. 동시성의 최종 보장은 실제 PostgreSQL 행 잠금에 기반하며 pg-mem 테스트만으로 운영 DB의 경합을 재현했다고 주장하지 않는다.

## 로컬 검증 결과

- 홈페이지: 프로덕션 빌드, ESLint, 단위 테스트 22개 통과.
- 홈페이지 HTTP 프록시: 관리자 인증, CSRF, 요청 경로 제한, 수분양자 세션 분리, 공개 날짜 전달 및 설정 저장 검사 통과.
- Playwright: 별도 할인액 입력 → 실제 판매가 계산 → 저장/새로고침 유지, 방막기 저장, 390px 모바일 가로 넘침 검사 통과. 저장/HTTP는 로컬 테스트 서버를 사용했고 PMS 저장 동작은 아래 별도 테스트에서 검증했다.
- PMS: 격리된 HTTP 서버 실행/종료, 백엔드 빌드, 단위 93개 스위트·488개 테스트, e2e 53개 스위트·289개 테스트 통과. 새 판매 설정 코드와 테스트의 ESLint도 통과.
- PMS의 기존 CMS 실제 PostgreSQL 신뢰성 테스트 1개 스위트·20개는 `CMS_SYNC_TEST_DATABASE_URL`이 없어 기본 설정대로 제외됐다.
- Kiosk: 단위 24개 스위트·89개 테스트, e2e 18개 스위트·46개 테스트 통과.

브라우저 검증은 기존 설치된 Playwright를 `SALES_PLAYWRIGHT_MODULE` 환경변수로 지정하여 `npm run test:pms-http`로 실행했다. 해당 변수가 없으면 HTTP 검사만 실행한다. 새 기능의 DB·API 회귀 테스트는 PMS `test/website-booking/website-sales.service.spec.ts`, `website-sales.e2e.spec.ts`에 있다.
