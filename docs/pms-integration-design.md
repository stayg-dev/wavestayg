# 양양 웨이브스테이지 · 최소 PMS 연동 설계

> 과거 설계 기록입니다. 2026-09-22 구현·설정 기준은 [PMS 예약 설정](./pms-booking-setup.md)을 따릅니다. 아래의 PMS 상태 재확인/역전파/일치화 제안은 폐기했습니다. 홈페이지 → PMS 판매일보 단방향만 허용합니다.

2026-09-11 개정. 일반 예약과 수분양자 예약 모두 웨이브스테이지 홈페이지에서 관리자가 확인·승인한다. 이번 변경은 설계 문서만이며 서버·DB·화면 구현이나 배포는 하지 않았다.

## 1. 구성

**기존 Next.js 홈페이지 → 기존 PMS API → 기존 PMS DB**

새 서버·별도 예약 DB·작업 큐를 추가하지 않는다. 공지는 기존 Vercel Blob을 그대로 쓴다. 홈페이지가 신청·본인 조회·취소 요청 및 관리자 검토·승인을 담당하고, 실제 예약 등록·재고·배정은 기존 PMS 기능을 사용한다.

**일반/수분양자 신청 → 홈페이지의 유형별 관리자 목록에서 확인 → 승인 버튼 → PMS 예약 등록 성공 → 확정** 순서다. 접수만으로 PMS 예약을 자동 생성하지 않는다. 금전 결제·추가 요금 정산은 현장에서 하고 홈페이지에는 조건만 안내한다.

신청 데이터의 저장 위치는 기존 PMS DB를 재사용하지만 승인 전 데이터는 별도 신청 테이블에만 존재한다. PMS의 실제 예약 목록·판매일보·재고에는 반영하지 않는다. 관리자 업무 화면을 홈페이지로 옮기는 것이며 저장소나 서버를 추가하는 변경은 아니다.

## 2. 새 데이터는 두 종류

| 데이터 | 최소 내용 |
|---|---|
| 수분양자 계정 | 화면 기본값은 호실·이름·전화번호·잔여 박수. 내부에 프로젝트·계정 ID·비밀번호 해시·사용 여부·혜택 기준 연도·올해 잔여·이월 잔여를 저장. 이월 만료는 기준 연도 3월 31일로 계산 |
| 예약 신청 | 프로젝트, 일반/수분양자 구분, 계정 또는 일반 조회 비밀번호 해시, 원래 신청 날짜·수량·인원·투숙객·연락처·희망 조건, 신청 당시 안내와 예상 요금(있을 때), 승인 조건·확정 금액·고객 합의 기록, 상태·버전, 취소 요청 시각, 확정 PMS 예약 ID 목록, 처리한 혜택 박수(수분양자만), 처리자·고객 안내·내부 메모, 최근 연동 오류 |

기존 PMS 예약·객실·사용자·권한·활동 로그를 재사용한다. 별도 재고 테이블, 계약 테이블, 정책 버전 테이블, 결제 테이블, 이벤트 발송 테이블을 신설하지 않는다. 기존 모델에 담을 수 있는 필드는 재사용한다.

계정의 로그인용 호실과 PMS 실제 호실은 매핑하지 않는다. 동일 타입 무료 조건 등은 계정 메모와 운영 안내를 보고 관리자가 판단한다.

호실 목록 등록 시 서버가 호실별 계정과 8자리 랜덤 초기 비밀번호를 자동 생성하고 사용자는 로그인 후 직접 변경할 수 있다. 이름·전화번호는 이후 입력할 수 있다. 같은 프로젝트의 기존 호실은 중복 등록·비밀번호 덮어쓰기를 하지 않는다. DB에는 password_hash만 저장한다. 분실 시 홈페이지 관리자가 새 8자리 랜덤 비밀번호를 재발급하며 변경·재발급 시 기존 세션은 무효화한다. 별도 비밀번호 관리 테이블이나 자동 발송 시스템은 추가하지 않는다.

스케줄러 대신 기존 PMS API의 공통 함수에서 계정의 기준 연도를 확인하고 연간 15박 부여·이월·이월 소멸을 DB에 반영한다. 로그인·내 정보·관리자 목록·승인 등에서 인증·권한 확인 후 필요한 계정을 갱신한다. 같은 계정 행 잠금으로 중복 부여를 막고 기존 예약의 숙박연도별 사용량을 반영한다. 상세 계산과 2026년 예외는 수분양자 설계를 따른다.

## 3. 화면은 최소로

홈페이지:
- 일반 예약 신청, 접수번호·조회 비밀번호를 통한 본인 신청 조회. 상세 기준은 [일반 예약 설계](./general-booking-design.md)를 따른다.
- 수분양자 로그인, 신청 및 내 신청 목록. 잔여 박수는 API에서 연도·만료를 갱신하고 승인·취소 결과를 반영한 값으로 표시.
- 날짜·객실 수·인원·투숙객 입력. 수분양자는 타입·호실 선택을 받지 않는다. 일반 고객의 희망 타입 선택은 일반 예약 설계의 별도 기준을 따른다. 실제 호실 선택과 온라인 결제 화면은 두 유형 모두 없다.
- 신청 대기는 “관리자 확인 후 확정됩니다”, 비용은 “현장 정산” 안내.

홈페이지 관리자:
- 기존 /admin 로그인·레이아웃을 재사용해 “공지 / 일반 예약 / 수분양자 예약 / 수분양자 계정” 메뉴를 둔다.
- /admin/reservations에서 일반 신청만 조회한다. 기본은 확인 대기이며 접수 시각·입실일·수량·인원·예약자·연락처·상태와 취소 요청·연동 확인 필요 건을 표시한다.
- /admin/owner-reservations에서 수분양자 신청만 별도 조회한다. 기본 목록은 승인 대기이며 취소 요청·연동 확인 필요 건을 함께 눈에 띄게 표시한다.
- 대기 건수, 접수 시각, 가까운 입실일, 계정 호실·날짜·수량·인원·잔여 박수를 표시한다. 행을 열어 보는 것만으로 처리 완료가 되지 않는다.
- 상세에서 승인·반려·취소 처리와 사유를 입력한다. 반려는 PMS 예약을 생성하지 않는다.
- /admin/owners에서 호실·이름·전화번호·잔여 박수를 관리하고 비밀번호를 재발급한다. 별도 관리자 로그인 체계를 만들지 않는다.

PMS에는 새 신청 검토 화면을 만들지 않는다. 홈페이지에서 승인 완료된 건만 기존 예약 업무로 들어간다. 일반·수분양자 신청은 같은 승인 서비스를 사용하되 관리자 목록과 유형별 검증을 분리한다. 일반 예약에 수분양자 혜택 조회·차감·복원을 적용하지 않는다. 승인 대기·연동 오류는 수동 새로고침과 화면 진입 시 조회하며 자동 알림 시스템은 추가하지 않는다.

## 4. 처리 흐름

1. 신청 테이블에 저장하고 접수번호를 반환한다. 재고·박수 차감 및 실제 PMS 예약 생성은 하지 않는다.
2. 관리자가 홈페이지의 해당 유형 승인 대기 목록에서 날짜·수량·인원·제공 조건을 확인한다. 일반 예약은 확정 요금과 고객 합의를, 수분양자는 잔여 박수·동일 타입 제공 조건을 확인한다. 실제 배정 가능 여부는 기존 PMS 정보를 참고한다.
3. 홈페이지에서 “승인 및 PMS 등록”을 누르면 Next.js 서버가 관리자 인증을 검사한 뒤 기존 PMS 백엔드의 승인 API를 호출한다.
4. 승인 API가 신청 상태·버전·기존 PMS 예약 조건을 재검증하고 기존 예약 서비스를 이용해 PMS 예약 생성과 신청 연결·확정을 같은 DB 트랜잭션으로 저장한다. 수분양자에만 잔여 검증과 무료 박수 차감을 함께 적용한다. 2실 생성도 전체 성공 또는 전체 롤백이다.
5. 성공 시에만 홈페이지에서 확정과 PMS 예약번호를 표시한다. 이용자도 본인 조회 화면에서 확정을 확인한다. 전화·문자 안내는 기존 운영 방식으로 직접 한다.

기존 PMS가 타입·호실 없는 예약을 지원하지 않으면 홈페이지 관리자 승인 상세에 PMS 등록에 꼭 필요한 배정값만 받는다. 수분양자 신청 화면에는 계속 타입·호실 선택을 넣지 않는다. 실제 PMS 필수값과 미배정 지원 여부는 구현 시 확인하며 가짜 타입·호실을 채우지 않는다.

PMS 수동 등록 후 홈페이지에 다시 연결하는 것을 기본 흐름으로 삼지 않는다. 승인 API 하나 안에서 기존 예약 서비스를 재사용하며 별도 큐·동기화 서버를 만들지 않는다.

신청 ID를 PMS 등록의 중복 방지키로 사용한다. 이미 성공한 승인을 다시 호출하면 기존 예약번호를 반환하고 예약·박수를 다시 생성·차감하지 않는다. 타임아웃은 성공 여부가 불명확하므로 상태 조회 후 같은 신청 ID로 재시도한다. 조회도 실패하면 “연동 결과 확인 필요”로 남기고 확정·실패를 추정하지 않는다.

명확한 연동 실패는 확정하지 않고 오류와 재시도 버튼을 관리자 대기 목록에 남긴다. 신청을 목록에서 숨기거나 백그라운드에서 자동 승인하지 않는다. 처리 상태·승인 시각·PMS 예약번호가 관리자의 완료 확인 기준이다.

## 5. 재고·취소

재고의 기준은 기존 PMS 예약이다. 일반·수분양자 확정 예약이 모두 여기에 등록되므로 별도 홈페이지 재고를 운영하지 않는다. 홈페이지에 정확한 실시간 잔여 객실 수나 자동 확정을 약속하지 않는다.

대기 신청은 철회할 수 있다. 확정 예약은 홈페이지 관리자 취소 요청 목록에서 확인한 뒤 처리한다. 취소 API는 기존 PMS 취소와 신청 상태를 함께 저장하고, 수분양자에만 혜택 복원을 적용한다. 성공한 뒤에만 취소 완료로 표시한다. 실패·타임아웃은 승인과 같은 조회·재시도 방식으로 처리한다. 최초 취소 요청 시각을 남겨 관리자 처리 지연으로 취소 기준이 달라지지 않게 한다. 일반 예약의 취소·현장 정산 기준은 별도 운영 안내를 적용한다.

일상적인 일반·수분양자 취소는 홈페이지를 처리 창구로 한다. PMS에서 직접 변경된 예약은 상세 조회 시 연결된 실제 상태를 확인해 “관리자 확인 필요”로 표시하고 정산·잔여 처리를 유형에 맞게 확인한다. 별도 양방향 동기화 엔진은 만들지 않는다.

타입·호실 배정 변경은 기존 PMS 업무로 처리한다. 배정·체크인만으로 무료 박수를 다시 차감하지 않는다. 현장 금전 환불은 시스템의 온라인 결제 상태와 연결하지 않는다.

기존 PMS의 중복 예약 검사와 재고 처리를 재사용하되 현재 코드가 보장하는 범위는 구현 시 확인한다. 별도 실시간 재고 동기화 엔진을 이번 범위에 넣지 않는다. 운영자 확인·기존 PMS 예약 등록을 거치는 방식의 한계를 안내한다.

## 6. 꼭 남길 서버 검증

- 수분양자 본인 신청만 조회·철회·취소 요청. 일반 조회는 접수번호와 조회 비밀번호를 검증하고 해당 신청에 한정된 세션을 발급한다. 전화번호·이름·접수번호만으로 조회를 허용하지 않는다.
- 비밀번호는 해시로 저장하고 로그인 시도 제한과 보호된 세션 쿠키를 적용한다. 사용자 변경은 현재 비밀번호를 확인하며 변경·재발급 후 기존 세션을 차단한다. 재발급으로 예약·혜택을 초기화하지 않는다.
- 기존 홈페이지 관리자 세션을 승인·반려·계정 수정 서버 API에서 검사한다. PMS 호출은 해당 프로젝트에 한정된 서버 전용 자격증명을 쓰고 브라우저에는 노출하지 않는다. 일반 수분양자 세션으로 승인 API를 호출할 수 없다.
- 중복 제출 방지용 요청 키와 상태·버전 검사로 재시도와 관리자 중복 확정을 막는다.
- 신청 상태·실제 PMS 예약·수분양자 잔여 박수 변경은 PMS DB의 같은 트랜잭션으로 저장한다. 기존 서비스에 공통 트랜잭션을 전달하는 데 필요한 변경만 한다.
- 응답 유실 후 재시도는 같은 신청 ID로 기존 결과를 반환한다. 승인·철회·반려·취소의 상태 경합도 서버에서 검사한다.
- 잔여 수정·승인·반려·취소는 기존 PMS 활동 로그에 홈페이지 관리자 주체와 사유를 남긴다. 현재 공용 비밀번호 로그인에서는 개인 관리자를 구분했다고 기록하지 않는다.

이는 별도 아키텍처가 아니라 기존 API 안에서 필요한 기본 검증이다.

## 7. 구현 순서

1. 계정·신청 데이터와 최소 API.
2. 홈페이지 일반·수분양자 각각의 승인 대기 목록·상세와 수분양자 계정 관리.
3. 공통 홈페이지 승인 → PMS 예약 생성 API, 수분양자만 혜택 차감, 실패·재시도 처리.
4. 일반 비회원 신청·조회와 수분양자 로그인·신청·조회, 공통 취소 요청·관리자 처리.

온라인 결제, 자동 객실 배정, 실시간 재고 API, 자동 승인, 스케줄러, 문자/알림톡 자동 발송, 별도 큐·원장·범용 정책 엔진은 이번에 만들지 않는다. 연간 부여·이월·만료만 기존 API 호출 안에서 간단한 공통 함수로 처리한다.

검증은 승인 전 PMS 예약 없음, 수분양자 전용 대기 목록, 관리자 API 접근 제한, 승인 성공 후에만 확정, 2실 전체 롤백, 연동 실패·응답 유실·재시도 중복 방지, 취소 상태와 잔여 처리에 집중한다. PMS 코드를 수정할 때는 해당 저장소의 필수 테스트·스키마·활동 로그 규칙을 따른다.

수분양자 운영 기준은 [수분양자 최소 설계](./owner-booking-design.md), 일반 고객 처리 기준은 [일반 예약 설계](./general-booking-design.md)를 따른다.
