# NICEPAY 인증결제 연동 설계

작성일: 2026-10-13 · 상태: 로컬 구현 완료, 운영 미적용

2026-10-13 요구사항 추가: **PG보다 먼저 홈페이지 관리자에서 실제 판매 요금 수정과 홈페이지 방막기를 제공한다. 요금·판매 차단·예약·결제·변경 이력의 모든 영속 데이터는 기존 PMS DB에서 관리한다.** 상세 화면과 저장 규칙은 [홈페이지 요금 및 방막기 관리 설계](./website-sales-settings-design.md)를 따른다.

2026-10-13 로컬 구현: `/admin/settings/`의 요금·할인액·방막기와 PMS 저장·견적 연결, NICEPAY 인증결제·서버 승인·망취소·관리자 전액 환불을 구현했다. `base_amount`, 별도 `discount_amount`, 서버 계산 `sale_amount`를 사용한다. 아래 최초 설계의 가격 차이와 테이블 제안은 착수 전 상태이며, 실제 구현·운영 적용 기준은 다음 절을 우선한다. 운영 DB 적용·실제 PG 요청·배포는 수행하지 않았다.

## 구현 및 운영 적용 기준 (2026-10-13)

홈페이지와 `C:/dev/HIO/stayg-pms/backend`를 함께 변경했다. 결제 영속 데이터는 PMS PostgreSQL에만 저장한다. 홈페이지 브라우저에는 주문별 조회용 HttpOnly 쿠키만 보관하고, MerchantKey·조회 토큰·인증 토큰은 공개 JSON과 로그에 노출하지 않는다. PG 결제창용 SignData와 일회성 ReturnURL은 공식 결제창 호출에 필요한 공개 요청 값이다.

| 항목 | 구현 |
|---|---|
| 일반 예약 | PMS 견적 및 설정 revision 확인 → 취소 규정 동의 → 15분 재고 확보 → 공식 `nicepay-pgweb.js`의 `goPay(form)` |
| PC / 모바일 복귀 | `/api/payments/return/`에서 form POST 수신, 원래 쿠키 없이 주문별 복귀 토큰과 PG 서명 검증. ASCII 프로토콜 값의 원문을 보존하며 EUC-KR/UTF-8 안내문은 저장하지 않음 |
| 결과 조회 | `/reservation/payment/?order=…`, 신청 번호·비밀번호 조회 시 다른 기기에서도 상태 쿠키 발급 |
| 관리자 | `/admin/payments/`: 결제·환불 상태, Moid/TID, 관리자 전액 환불, NICEPAY에서 확인한 거래 결과의 수동 대사 |
| 정책 | `/admin/settings/`의 결제·취소 규정 버전/본문, 내용 변경 시 버전 변경 필수, 주문에 동의한 본문·버전·시각 저장 |
| DB | `website_payment_orders`, `website_payment_attempts`, `website_payment_refunds`; `website_applications.payment_order_id`, `sales_daily_reports.website_payment_order_id` 연결 |
| 재고와 수납 | 대기 판매일보는 `RESERVED`·수납 0원, 승인 확정 후 카드 항목에 실제 청구액 반영. 고객 접수 알림은 승인 후, 취소 알림은 환불 확정 후 기존 PMS 발송 큐에 저장 |
| 기존 흐름 보호 | 수분양자 무료·현장 정산 유지. 온라인 결제 예약의 직접 취소·삭제·금액/일정 변경·복사 차단. 결제 완료 후 기존 금액을 보존한 객실 배정·투숙객 정보 수정 및 프런트 체크인 지원 |

승인·환불 HTTP 통신은 DB 트랜잭션 밖에서 수행한다. 5초 주기의 PMS 스케줄러가 DB에 작업 상태와 120초 lease를 먼저 저장한다. 승인 응답 유실 또는 승인 중 서버 재시작 시 승인을 다시 보내지 않고 망취소로 전환한다. 검증된 응답은 판매일보 반영 전에 별도로 커밋하므로 후속 DB 오류는 청구 없이 로컬 반영만 재시도한다. 망취소는 최대 3회까지 확인하고 불명확하면 `manual_review`로 전환하며 재고를 유지한다. 일반 환불 응답이 불명확하면 자동 재전송하지 않는다.

관리자 수동 대사는 NICEPAY 관리자에서 TID·주문번호·승인/취소 금액을 확인한 뒤 확인자·시각·근거를 입력하는 절차다. **대사 버튼은 PG에 승인·취소 요청을 보내지 않으며 확인된 결과만 PMS에 기록한다.** 처리 중인 거래는 수동 대사할 수 없다. 결과가 불명확한 거래를 임의로 실패 처리해서 객실을 다시 판매하지 않는다. 승인 완료와 호텔의 예약 확정 알림은 별개다.

### 적용 순서

1. 기존 PMS DB 백업 후 미적용된 `backend/.db/patches/20261013_website_sales.sql`, 다음으로 `20261013_website_payments.sql`을 적용한다. `schema.ddl.sql`에도 같은 테이블·열을 반영했다. 코드에서 자동으로 운영 스키마를 변경하지 않는다.
2. PMS 환경 변수는 `backend/.env.example`을 따른다. `NICEPAY_ENABLED=false` 상태로 PMS와 홈페이지를 배포한다. 홈페이지에는 기존 `PMS_PROJECT_ID`, `PMS_API_KEY`, 관리자 인증만 필요하다. PG 키는 PMS에만 둔다.
3. PMS에 `NICEPAY_MID`, `NICEPAY_MERCHANT_KEY`, `NICEPAY_ENVIRONMENT=test`, `WEBSITE_PUBLIC_ORIGIN=https://실제홈페이지도메인`, `PAYMENT_DATA_ENCRYPTION_KEY`를 설정한다. 암호화 키는 독립적인 무작위 32바이트의 base64 값이며 모든 PMS 인스턴스에서 동일해야 한다. 서버 재시작 시 새로 만들지 않는다. 대기 거래가 있는 동안 키·MID를 바꾸지 않는다.
4. **`NICEPAY_ENVIRONMENT=test`는 기록용 구분이다. 실제 테스트 여부는 NICEPAY가 발급한 MID/키에 의해 결정되므로 테스트 MID/키를 사용해야 한다.** 이 구현은 테스트와 운영 모두 공식 인증결제 도메인만 호출한다.
5. 관리자에서 실제 요금·별도 할인액·판매일·방막기·취소 규정을 저장한다. PG 키 또는 규정이 준비되지 않으면 활성화 상태여도 신규 카드 결제를 차단한다. `NICEPAY_ENABLED=false`에서는 기존 일반 현장 정산 신청을 유지한다.
6. 테스트 가맹점으로 PC와 모바일 브라우저의 인증·승인·전액 취소, 앱카드 복귀, 결제창 닫기, 서명 오류, 중복 복귀, 통신 단절, 실제 PostgreSQL 동시 재고 경합을 확인한다. 현재 로컬 검증은 PG 응답 대체와 pg-mem을 사용했으며 실제 승인/취소나 실 PostgreSQL 잠금 경합 검증을 대신하지 않는다.
7. 운영 MID 계약/도메인/네트워크 설정 확인 후 사용자가 운영 키와 `NICEPAY_ENVIRONMENT=production`, `NICEPAY_ENABLED=true`로 전환한다. PMS 스케줄러가 계속 실행되어야 승인·만료·환불을 처리할 수 있다. 신규 결제만 중단할 때는 `NICEPAY_ENABLED=false`로 바꾸고 기존 키와 스케줄러를 유지한다.

Reverse proxy/APM은 `/api/payments/return/`의 query token과 POST 본문을 로그에 기록하지 않도록 설정한다. 이 경로는 PG의 외부 form POST와 303 리다이렉트를 허용해야 한다. 홈페이지 결제창 요청과 PMS 승인/취소 요청은 EUC-KR, 응답 요청은 `CharSet=utf-8`이다. HTTPS 연결 5초·전체 요청 35초·응답 64KiB 제한과 공식 호스트/경로 허용 목록을 적용한다.

현재 범위는 일반 예약의 카드 전액 결제와 입실 전 관리자 전액 취소다. 부분 환불·가상계좌·정산 수수료 계산·거래 조회 API 자동 대사는 포함하지 않는다. 온라인 결제 예약의 키오스크 체크인은 차단하며 프런트에서 처리한다. 객실 간 이동·자동 노쇼 처리도 보호 대상이다. 기존 PMS 폼에서 객실 배정/체크인하는 운영 경로를 사용하고 금액·일정 변경은 전액 환불 후 신규 예약으로 처리한다. 실제 PG 테스트 시 해당 가맹점 응답 규격도 확인한다.

공식 근거: [결제창](https://developers.nicepay.co.kr/docs/pg/auth/payment-window/), [승인](https://developers.nicepay.co.kr/docs/pg/auth/authorization/), [망취소](https://developers.nicepay.co.kr/docs/pg/auth/net-cancel/), [승인 취소](https://developers.nicepay.co.kr/docs/pg/auth/payment-cancel/).

### 로컬 검증 결과

- 홈페이지 프로덕션 빌드, ESLint, 단위 테스트 24개 통과.
- HTTP/Playwright: 관리자 인증·CSRF·가격 재계산 위임·HttpOnly 쿠키·쿠키 없는 모바일 복귀·PC SDK 콜백·결제 결과·관리자 환불 요청·390px 화면 넘침 검사 통과. SDK와 PMS HTTP 응답은 로컬 대체 서버를 사용했다.
- PMS 격리 서버 실행/종료와 빌드, 단위 97개 스위트·502개 테스트, e2e 54개 스위트·290개 테스트 통과. 최종 수정 후 관련 결제·판매일보·알림 e2e 42개도 재확인했다.
- PMS의 기존 실 PostgreSQL CMS 테스트 1개 스위트·20개는 `CMS_SYNC_TEST_DATABASE_URL` 미설정으로 제외됐다. 새 결제 DB 검증은 pg-mem으로 수행했다.
- 키오스크 단위 24개 스위트·89개 테스트, e2e 18개 스위트·46개 테스트 통과. 신규 결제 코드·테스트 ESLint 및 양쪽 변경분 공백 검사 통과.

배포 전 원래 MID의 환불 가능 거래가 남아 있다면 해당 MID/키를 계속 유지한다. 이 버전은 여러 MID의 동시 운영이나 자동 키 전환을 지원하지 않는다.

이하 내용은 최초 설계와 검토 근거를 보관한 것이다.

웨이브 스테이지의 일반 예약에 NICEPAY 카드결제를 연결한다. 홈페이지는 결제창과 결과 화면을 제공하고, 기존 PMS 백엔드가 금액 계산, 주문 저장, 승인·취소, 재고 확보와 복구를 담당하는 구성을 권장한다. 결제 정보도 기존 PMS PostgreSQL에 저장한다.

**권장 흐름은 요금 확인 → 객실 임시 확보 → 카드 인증 → 서버 승인 → 결제 완료 및 PMS 접수 → 호텔 확인이다.** 카드 결제 완료와 호텔의 예약 확인은 별도 상태로 관리한다. 1차 범위는 일반 예약의 전액 카드결제와 관리자 환불이며, 수분양자 무료·현장 정산 흐름은 별도 경로로 유지한다. 이는 이 문서의 제안 범위이며 운영 정책 확정을 뜻하지 않는다.

## 1. 기준 자료와 현재 구현

결제 규격은 사용자 제공 `[NICEPAY]인증결제-2.1.3.pdf`를 기준으로 한다. 문서 버전은 2.1.3, 개정일은 2025-12-31이며 총 32쪽이다. 주요 참조는 흐름 p.5~10, 결제창 p.11~15, 승인 p.16~19, 망취소 p.20~21, 승인 취소 p.22~23, 서명 p.24~27, 부분취소 유의사항 p.30~32다. 문서 속 예시 계정·키는 운영 설정에 사용하지 않는다.

2026-10-13 공식 개발자 문서에서도 동일한 인증결제 계열을 확인했다. 이 설계는 `nicepay-pgweb.js`, `MID`, `MerchantKey`, `SignData` 방식이다. 별도 제품의 `AUTHNICE.requestPay()`, clientKey/secretKey 방식과 혼용하지 않는다. 계약된 MID가 이 규격용인지 NICEPAY에 확인한다.

| 현재 코드에서 확인한 항목 | PG 도입 시 의미 |
|---|---|
| 홈페이지 `src/components/website-booking.tsx`에서 PMS 견적을 조회하고 신청 | 결제 총액도 PMS 견적을 기준으로 고정해야 함 |
| `src/app/api/pms/[...path]/route.ts`가 서버 키로 PMS 호출, 브라우저의 `quoted_amount`는 무시 | 기존 서버 신뢰 경계를 재사용 |
| PMS `WebsiteBookingService.apply()`가 같은 트랜잭션 안에서 `registerApplication()` 호출 | 현재는 신청만으로 판매일보가 생성됨. 결제 전용 준비 단계를 분리해야 함 |
| PMS 판매일보는 `RESERVED`, 신청은 `registered`; 일반 결제 항목은 `현장결제 예정` | 등록 여부만으로 온라인 결제 완료를 판단할 수 없음 |
| 신청 접수와 호텔 확정 알림톡 처리, PMS에서의 취소 경로가 존재 | 결제 상태에 따른 발송·취소 조건을 모든 진입점에 적용해야 함 |
| 일반 조회는 신청 UUID와 비밀번호를 POST로 검증 | 결제 결과 조회에 사용할 제한된 세션을 추가해야 함 |
| `pms()`의 요청 제한은 25초 | PG 승인·망취소를 이 프록시 요청 하나에 묶으면 시간 부족 가능 |
| 홈페이지 공통 예약 버튼은 준비중 안내 | 결제 검증 완료 후 공개 동작을 별도로 전환해야 함 |

위 내용은 로컬 홈페이지와 `C:/dev/HIO/stayg-pms/backend` 코드 기준이다. 운영 서버의 배포 상태를 의미하지 않는다. `docs/pms-booking-setup.md`의 2026-09-22 기록에는 관리자 승인 후 등록·단방향 처리라고 되어 있지만, 현재 코드는 자동 등록과 PMS 취소 연계를 포함한다. PG 구현은 현재 코드의 동작을 기준으로 하고 기존 문서도 구현 시 함께 갱신한다.

## 2. 결제 전에 해결할 요금 차이

현재 화면과 PMS 가격 계산이 일치하지 않는다. 홈페이지 `seasonal-rate-table.ts`와 `rate-guide.tsx`는 비수기 금액에서 5,000원을 할인해 표시하지만, PMS `application/website-booking/pricing.ts`는 기존 객실 금액을 계산한다. 예를 들어 스탠다드 더블의 표시 시작가는 50,000원이고 PMS 기본 객실료는 170,000원이다. 이 상태로 결제를 공개하면 고객이 본 가격과 청구 금액이 달라진다.

구현 첫 단계에서 PMS를 유일한 실제 요금 계산 주체로 정하고 다음 값을 주문에 저장한다.

관리자가 홈페이지의 `설정 > 요금 관리`에서 입력한 실제 판매가를 PMS DB에 저장하고, 공개 요금표·예약 견적·PG 청구가 이 값을 공통으로 사용한다. 코드 상수는 최초 이관 자료로만 사용한다. `설정 > 방막기`의 전체 접수 중지와 날짜·객실 타입별 판매 차단도 PMS 서버가 견적·신청·결제 준비에서 검사한다. 기존 예약과 유효한 결제 확보 건의 처리 기준은 상세 설계의 정책을 적용한다.

- 숙박일별 객실 기준 요금, 시즌과 요일 구분, 객실 수
- 숙박일별 할인액과 할인 정책 버전
- 추가 인원·침구 금액, 최종 원화 정수 총액
- 견적 버전, 유효기간, 취소 규정 버전과 고객 동의 시각

비수기 할인은 **객실 1실·1박당 5,000원**으로 적용하는 안을 권장한다. 비수기 2박·2실이면 객실료 할인은 총 20,000원이고 부가서비스는 별도다. 시즌 경계를 걸치는 숙박은 각 숙박일로 판정한다. 할인 기간, 금·토 포함 여부, 중복 할인과 환불 배분은 운영 정책으로 확정한다. 현재 표시상 비수기는 9월~4월이며 7월 1~14일·8월 16~31일 등 시즌표 공백도 결제 도입 전에 채워야 한다.

최종 확인 화면은 서버 견적의 명세를 표시한다. 준비 단계에서 가격이 바뀌면 새 금액에 동의를 받은 후 결제창을 연다. 인증이 진행 중인 주문은 금액을 수정하지 않으며, 변경이 필요하면 기존 시도를 종료한 뒤 새 견적과 시도를 만든다. 화면의 취소선 금액을 실제 청구 기준으로 사용하지 않는다.

## 3. 권장 구성과 책임

| 구성 | 책임 |
|---|---|
| Next.js 홈페이지 | 예약 입력, 서버 견적 표시, 공식 결제창 호출, 인증 응답 전달, 결제 상태 조회 |
| 홈페이지 관리자 설정 | 실제 요금·판매 차단 편집과 변경 이력 조회. PMS API를 통해 저장 |
| Next.js 전용 결제 API | 요청 크기·형식 제한, 고객 세션과 관리자 인증, PMS 서버 통신, 결과 페이지 리다이렉트 |
| PMS 결제 서비스 | 주문·재고·결제 상태, 서명 생성·검증, NICEPAY 승인·망취소·환불 |
| PMS DB 작업 처리기 | 영속 작업 실행, 타임아웃·프로세스 종료 복구, 만료 처리, 재시도·운영 확인 대상 관리 |
| NICEPAY 결제창 | 카드사 인증과 결제수단 입력 |

`MerchantKey`는 PMS 서버의 비밀 환경변수에만 둔다. Next.js와 브라우저는 키를 받지 않는다. 브라우저에는 결제창에 필요한 공개 필드와 서버가 만든 `SignData`만 반환한다. 홈페이지나 PMS가 카드번호·CVC·카드 비밀번호를 직접 수집하지 않는다.

기존 PMS에 DB 기반 알림톡 작업과 스케줄 실행 구조가 있으므로 결제 작업도 같은 운영 기반을 활용할 수 있다. 결제용 테이블과 처리기는 분리하고, 인메모리 플래그만으로 중복 실행을 막지 않는다. 여러 PMS 인스턴스에서도 DB 잠금·작업 소유권으로 하나의 실행자만 외부 결제를 호출하도록 한다.

## 4. 정상 결제 흐름

1. 고객이 날짜·타입·수량·인원·침구를 선택하고 PMS 견적을 확인한다.
2. 고객이 조회 비밀번호와 약관 동의를 제출하면 결제 준비 API가 서버에서 요금과 재고를 다시 확인한다.
3. PMS가 신청, 주문, 결제 시도와 객실 임시 확보를 하나의 DB 트랜잭션으로 저장한다. 한 객실이라도 확보하지 못하면 전부 롤백한다.
4. PMS가 `Moid`, `Amt`, `EdiDate`, `SignData`, `ReturnURL` 등 인증 요청 필드를 생성한다. 브라우저가 공식 스크립트의 `goPay(form)`을 호출한다.
5. PC는 `nicepaySubmit()`에서 폼을 반환 API로 제출한다. 모바일은 NICEPAY가 `ReturnURL`로 폼을 POST한다. 두 경로를 같은 인증 결과 처리 서비스에 연결한다.
6. 반환 API와 PMS가 주문·시도·금액·서명을 검증한다. 인증 성공(`AuthResultCode=0000`)일 때만 승인 작업을 영속 저장한다.
7. PMS 작업 처리기가 해당 시도를 잠금으로 선점한 뒤, 인증 응답의 `NextAppURL`로 승인 요청을 보낸다. 요청 직전 처리 상태를 커밋하고 PG 통신 중 DB 트랜잭션을 열어 두지 않는다.
8. 카드 승인 성공(`ResultCode=3001`) 및 응답 검증 후 결제 내역과 PMS 결제 항목을 저장하고 임시 확보를 정식 접수로 전환한다. 같은 트랜잭션에 필요한 알림 이벤트도 저장한다.
9. 고객 결과 화면은 서버 상태를 조회해 `결제 완료 · 호텔 확인 대기`를 표시한다. 호텔 확인과 확정 알림톡은 별도 절차로 유지한다.

인증 반환은 최종 결제 성공 통보가 아니다. 브라우저 콜백 실행, HTTP 200, 인증 성공 코드만으로 결제 완료나 예약 확정을 표시하지 않는다. 브라우저를 닫아도 이미 저장된 승인 작업과 복구 작업은 PMS에서 계속 처리한다.

## 5. 객실 임시 확보와 만료

권장안은 기존 `RESERVED` 판매일보의 재고 점유 기능을 재사용하되 **온라인 결제 대기**를 식별하는 상태와 만료시각을 추가하는 것이다. 이를 위해 `registerApplication()`의 재고 확보·판매일보 생성·접수 완료·알림 발송 책임을 분리한다.

임시 확보 시 생성한 판매일보를 승인 후 갱신하며 다시 생성하지 않는다. 미결제 확보 건은 객실 수량에서 차감하되 수납 완료·정산·확정 알림 대상에는 포함하지 않는다. 기존 판매일보 집계가 이 구분을 지원하는지 확인하고, `현장결제 예정` 항목을 실제 카드 수납으로 오인하지 않도록 결제상태와 보고서를 함께 수정한다. 이 분리가 불가능하면 별도 확보 테이블이 필요하며, 그 경우 PMS·홈페이지·기타 재고 차감 경로 모두에서 확보량을 반영해야 한다.

초기 확보시간은 **15분을 제안**한다. NICEPAY 인증 유효시간과 모바일 카드 앱 왕복 시간을 확인한 뒤 설정값으로 확정한다. 고객에게 남은 시간을 표시하되 서버 시간이 최종 기준이다.

| 만료 시 결제 상태 | 처리 |
|---|---|
| 결제창 미진입 또는 인증 대기 | 시도를 만료시키고 확보 해제 |
| 인증 결과 검증·승인 처리 중 | 만료 작업이 재고를 해제하지 않음 |
| 승인 결과 불명확 | 신규 결제 차단, 망취소·거래 확인 후 확보 해제 여부 결정 |
| 결제 완료 | 확보를 유지하고 자동 만료 대상에서 제외 |

마지막 객실에 대한 동시 요청, 승인과 만료, 관리자 취소와 승인에 동일한 잠금 순서와 버전 검사를 적용한다. 단순 프런트엔드 타이머나 `nicepayClose()` 이벤트만으로 확보를 해제하지 않는다. 호텔에서 임시 확보 건을 수동 삭제·체크인·확정하는 기능도 결제 상태 검사로 막아야 한다.

## 6. NICEPAY 요청과 검증 규격

PDF p.11~27의 규격을 구현 계약으로 사용한다. [공식 결제창 문서](https://developers.nicepay.co.kr/docs/pg/auth/payment-window/)와 [승인 문서](https://developers.nicepay.co.kr/docs/pg/auth/authorization/)에서도 흐름과 필드를 확인할 수 있다.

| 단계 | 주요 필드와 규칙 |
|---|---|
| 결제창 | `https://pg-web.nicepay.co.kr/v3/common/js/nicepay-pgweb.js`; `goPay(form)` 호출 |
| 인증 요청 | `GoodsName`, `Amt`, `MID`, `EdiDate`, `Moid`, `SignData`, `PayMethod=CARD`, `ReturnURL` |
| 인증 응답 | `AuthResultCode`, `AuthToken`, `MID`, `Moid`, `Amt`, `Signature`, `TxTid`, `NextAppURL`, `NetCancelURL` |
| 승인 요청 | `TID=TxTid`, `AuthToken`, `MID`, `Amt`, `EdiDate`, `SignData` |
| 승인 성공 | `ResultCode=3001`, 예상 주문과 일치하는 `MID/Moid/TID/Amt/PayMethod`, 유효한 `Signature` |
| 망취소 | 인증 응답의 `NetCancelURL` 사용, 승인 요청 계열 필드와 `NetCancel=1` |
| 일반 승인 취소 | `https://pg-api.nicepay.co.kr/webapi/cancel_process.jsp`; 별도 취소 주문번호와 `CancelAmt`, `CancelMsg`, `PartialCancelCode` 등 |

서명은 구분자 없이 문자열을 이어 붙인 SHA-256의 hex 표현이다. HMAC이나 키의 Base64 디코딩을 임의 적용하지 않는다.

| 용도 | 해시 입력 순서 |
|---|---|
| 인증 요청 `SignData` | `EdiDate + MID + Amt + MerchantKey` |
| 인증 응답 `Signature` | `AuthToken + MID + Amt + MerchantKey` |
| 승인 요청 `SignData` | `AuthToken + MID + Amt + EdiDate + MerchantKey` |
| 승인 응답 `Signature` | `TID + MID + Amt + MerchantKey` |
| 망취소 요청 `SignData` | `AuthToken + MID + Amt + EdiDate + MerchantKey` |
| 일반 취소 요청 `SignData` | `MID + CancelAmt + EdiDate + MerchantKey` |
| 취소 응답 `Signature` | `TID + MID + CancelAmt + MerchantKey` |

`Amt`는 원 단위 정수다. 서명 검증에는 수신 문자열의 원형을 보존하고, 주문 금액 비교에는 숫자로 변환한 값을 사용한다. 응답 금액의 선행 0 처리와 서명 계산을 테스트 MID의 실제 전문으로 검증한다. SHA-256 예제는 PDF p.24~27의 규칙과 대조하되, p.27 예제는 변수와 평문에 표시된 MID가 다르므로 예제 출력값을 무조건 정답으로 복사하지 않는다.

인증 `Signature`는 주문번호·URL 전체를 서명하는 구조가 아니다. 따라서 서명 일치만으로 요청 전체를 신뢰하지 않는다. 저장된 결제 시도와 주문번호, 서버 생성 반환 토큰, 거래 ID의 유일성, 금액과 결제수단을 함께 확인하고 승인 응답의 `Moid/TID`를 다시 대조한다. 같은 `TID`를 다른 주문에 연결할 수 없게 DB 제약을 둔다.

### 인코딩과 통신

PDF는 form-urlencoded/EUC-KR을 기본으로 명시하며 `CharSet=utf-8` 응답 옵션을 제공한다. 홈페이지 자체는 UTF-8을 유지하고 결제 어댑터에서 필요한 변환만 수행한다. `CharSet`을 설정했다고 모든 요청 본문이 UTF-8을 허용한다고 가정하지 않는다.

- 서버 승인 필수값은 영문·숫자이며, 한글 취소 사유와 구매자명은 EUC-KR byte 기준 길이·인코딩을 검증한다. 필요하면 PMS에 `iconv-lite`를 추가한다.
- EUC-KR 폼을 `request.formData()`나 UTF-8 전용 파서로 무조건 읽지 않는다. raw body 크기 제한 후 percent-decoding과 문자 인코딩 변환을 순서대로 적용한다.
- `GoodsName` 40 byte, `BuyerName` 30 byte, `Moid` 64 byte 등 PDF의 byte 제한을 적용한다. 한글 이름을 임의 훼손하지 않도록 결제용 표시값 생성 규칙을 정한다.
- 응답은 JSON을 사용하고 문서에 없는 추가 필드는 허용한다. 필수값 누락·중복 파라미터·잘못된 타입·비정상 크기는 거절한다.
- `EdiDate`는 서버에서 `Asia/Seoul`의 `YYYYMMDDHHmmss`로 생성한다. 서버 시간 동기화를 확인한다.
- PDF p.6의 연결 5초, 읽기 30초를 기준으로 통신 제한을 구성한다. 승인 후 망취소까지 이어질 수 있으므로 Next.js의 25초 프록시 안에서 전체 작업을 끝내도록 설계하지 않는다.

### 응답 URL 검증

승인은 응답받은 URL을 사용하되 다음 HTTPS 호스트와 경로만 허용한다. 사용자가 보낸 임의 URL로 서버 요청을 보내지 않는다. 리다이렉트는 따라가지 않는다.

- 승인: `dc1-api.nicepay.co.kr` 또는 `dc2-api.nicepay.co.kr`의 `/webapi/pay_process.jsp`
- 망취소: 같은 두 호스트의 `/webapi/cancel_process.jsp`
- 일반 취소: 서버 설정에 고정된 `pg-api.nicepay.co.kr/webapi/cancel_process.jsp`

임의 포트·사용자정보·fragment·예상하지 않은 query는 거절한다. 허용 목록 변경은 공식 규격 확인 후 서버 설정으로 반영한다. DC1을 DC2로 임의 교체하거나 승인 URL을 한 곳으로 고정하지 않는다.

## 7. 저장 모델과 상태

기존 신청의 `registered` 상태에 결제 의미를 덧씌우지 않는다. 예약 업무 상태, 결제 상태, 알림 발송 상태를 각각 보관한다. 아래 테이블·필드명은 신규 제안이다.

| 데이터 | 주요 필드 |
|---|---|
| `website_payment_orders` | `id`, `project_id`, `application_id`, `amount`, `currency=KRW`, 견적 스냅샷·버전, 동의 정책·시각, `hold_expires_at`, `payment_status`, `booking_review_status`, `version` |
| `website_payment_attempts` | `id`, `order_id`, `moid`, `mid`, `tid`, `status`, `amount`, 반환 토큰 해시, `auth_token_encrypted`, 검증된 PG URL, 요청·응답 코드, 승인번호·시각, 부분취소 가능 여부 |
| `website_payment_refunds` | `id`, `order_id`, `attempt_id`, 유일한 취소 `moid`, 취소 요청 키, 원승인 TID, 금액·사유·정책 버전, 상태, 취소번호·잔액·시각, 처리자 |
| `website_payment_jobs` | 작업 종류, 대상 ID, 상태, 실행 가능 시각, 시도 횟수, 작업 잠금·만료시각, 요청 시작시각, 마지막 오류 분류 |
| 기존 활동 로그 | 상태 변경 전후, 주문·시도·환불 ID, 시스템 또는 관리자 주체, 사유 |

주문은 하나의 청구 단위이고, 결제 시도는 결제창을 새로 여는 단위다. 재시도에는 새 `Moid`를 발급한다. 서버 내부 신청 UUID를 고객이 제출한 그대로 PG 주문번호로 신뢰하지 않으며, `WS` 접두어와 영숫자 난수 조합 등으로 64 byte 이내의 고유 번호를 만든다.

필수 제약은 `(환경, MID, Moid)` 유일성, `(환경, MID, TID)` 유일성, 주문당 활성 결제 시도 최대 1개, 결제 완료 주문에 대한 신규 승인 금지, 환불 요청 키 유일성이다. 환불 합계는 성공 건과 진행 중 예약 금액을 함께 계산해 승인액을 넘지 않게 한다. 같은 중복 제출 키에 다른 입력이 오면 기존 결과를 반환하는 대신 409로 거절한다.

| 결제 시도 상태 | 의미와 가능한 다음 처리 |
|---|---|
| `prepared` | 주문·확보 저장, 인증 시작 가능 |
| `auth_received` | 인증 응답 검증 완료, 승인 작업 대기 |
| `approving` | 승인 요청 시작 기록 완료. 재진입 시 무조건 재승인하지 않음 |
| `paid` | 승인 응답 검증 및 로컬 저장 완료 |
| `failed` | 인증 실패 또는 결제 미성립이 확인됨 |
| `expired` | 승인 진행 전 유효기간 만료 |
| `recovery_pending` | PG 처리 여부가 불명확, 망취소 또는 조회 필요 |
| `net_cancelled` | 망취소 성공을 검증해 결제 해소 확인 |

주문 수준에는 별도로 `refund_pending`, `partially_refunded`, `refunded`, `manual_review`를 표현한다. 부분환불 이력 때문에 원승인 금액을 덮어쓰지 않는다. 카드 승인 원금, 누적 성공 환불액, 잔액을 모두 보존한다.

PG와 DB는 하나의 원자적 트랜잭션으로 묶을 수 없다. `approving` 이후 프로세스가 종료되면 다음 처리기가 승인 성공·실패를 추정하지 않고 복구 경로로 들어간다. 작업 잠금 만료가 동일 승인 요청의 자동 재전송 허가를 뜻하지 않는다.

## 8. 홈페이지 API와 PMS 계약

아래 경로는 최초 설계 제안이다. 실제 구현 경로는 문서 상단의 구현 기준 및 `WebsitePaymentController`를 따른다. 결제 도메인 로직은 PMS에 두고 Next.js는 제한된 경로만 전달한다.

| Next.js 경로 | 입력과 권한 | 결과 |
|---|---|---|
| `POST /api/payments/prepare/` | 예약 입력, 견적 버전, 동의, 제출 키; same-origin·속도 제한 | 주문·확보 생성, 결제창 필드, 만료시각, 제한 세션 |
| `POST /api/payments/nicepay/return/` | PC·모바일 인증 결과 폼과 반환 토큰 | PMS에서 검증·작업 저장 후 고정 결과 화면으로 303 이동 |
| `GET /api/payments/{orderId}/` | 해당 주문 조회 세션 | 금액·상태·고객 메시지. 키·AuthToken·내부 URL 제외 |
| `POST /api/payments/{orderId}/retry/` | 주문 소유 권한과 제출 키 | 이전 시도가 안전하게 끝난 경우만 새 시도 |
| `POST /api/payments/lookup-session/` | 신청 UUID·조회 비밀번호 | 해당 신청·주문만 조회 가능한 짧은 세션 |
| `POST /api/admin/payments/{orderId}/refunds/` | 기존 관리자 인증, 금액·사유·버전·중복 방지키 | 환불 작업 접수와 상태 |
| `POST /api/admin/payments/{orderId}/reconcile/` | 관리자 인증, 사유 | 결과 확인 작업 접수. 임의 성공 처리 금지 |

PMS에는 `website/payments/prepare`, `website/payments/auth-result`, 주문 상태·재시도·환불 API와 내부 작업 서비스를 추가한다. 기존 website-key 검증을 유지하고 관리자 환불 경로는 Next.js의 `requireAdmin()`과 PMS 프로젝트 권한을 함께 거친다. PMS UI의 결제 취소도 같은 서비스로 연결한다.

반환 API는 PG의 cross-site POST를 받아야 하므로 기존 catch-all의 `sameOrigin()` 검사를 그대로 적용할 수 없다. 이 경로만 별도 Route Handler로 만들고 서명·반환 토큰·주문 검증을 적용한다. 나머지 쓰기 API의 same-origin 검사는 유지한다. PG의 POST는 브라우저를 통해 들어오므로 PG 서버 IP만 허용하는 방식으로 인증하지 않는다.

SameSite 쿠키는 모바일 cross-site POST에 없을 수 있다. 반환 처리 자체는 쿠키 없이 검증할 수 있어야 한다. 주문 준비 시 저장한 1회성 반환 토큰을 검증하고, 브라우저에 다시 돌아온 후 별도 조회 권한을 설정한다. 결과 조회 권한은 결제·환불 권한을 갖지 않는다. 토큰이 URL을 거칠 경우 로그를 가리고 1회 교환 후 토큰 없는 결과 주소로 이동하며 `Referrer-Policy: no-referrer`를 적용한다. UUID만 아는 사람에게 예약자·전화번호를 공개하지 않는다.

반환 API는 PMS가 인증 결과와 작업을 영속 저장한 뒤에만 접수 완료로 응답한다. 응답 유실로 같은 반환이 다시 들어오면 동일 결과를 반환한다. 브라우저에 돌려준 뒤 메모리에서만 승인 작업을 실행하는 방식은 사용하지 않는다. 승인 작업은 즉시 실행을 시도하고 DB 작업 처리기가 누락을 회수한다. NICEPAY 인증 토큰 유효시간은 담당자 확인 후 작업 지연 한도에 반영한다.

## 9. 오류와 복구

[공식 망취소 문서](https://developers.nicepay.co.kr/docs/pg/auth/net-cancel/)와 PDF p.20~21에 따라 승인 응답을 받지 못했거나 정상 처리하지 못한 경우 망취소로 거래 불일치를 해소한다. 승인 재시도와 망취소를 동시에 실행하지 않는다.

| 상황 | 서버 처리 | 고객 표시 |
|---|---|---|
| 결제창 로딩 실패·사용자 닫기 | 승인 여부 조회, 미진행이면 재시도 허용 또는 확보 만료 | 결제를 완료하지 못했습니다 |
| 인증 실패 | 승인 미호출, 실패 코드 기록 | 다른 수단으로 다시 시도 안내 |
| 인증 서명·주문·금액 불일치 | 승인 차단, 보안 이벤트 기록 | 결제 정보를 확인할 수 없습니다 |
| 승인 명확한 거절 | 실패 기록, 주문 상태 재조회 후 재시도 허용 | 카드사 거절 안내 |
| 승인 요청 타임아웃·연결 종료 | `recovery_pending`, 저장된 TID·토큰으로 망취소 | 처리 결과 확인 중, 중복 결제 금지 |
| 승인 응답 서명·금액 불일치 또는 DB 저장 실패 | 성공 표시 금지, 같은 거래의 망취소·복구 | 처리 결과 확인 중 |
| 망취소 응답도 유실 | 상태 확인 작업과 관리자 경보, 새 승인 차단 | 확인 중 및 주문번호·문의 경로 |
| 결제 저장 후 알림톡 실패 | 결제 유지, 알림만 재시도 | 결제 완료 표시 유지 |
| 결제 완료 후 호텔 제공 불가 | 관리자 환불·예약 취소 절차 | 환불 진행 상태 표시 |

망취소 성공은 PDF상 `2001`이며 서명과 거래·금액을 검증한다. `기취소`, `거래 없음` 등 기타 응답을 임의로 성공으로 해석하지 않는다. 결제 조회 API의 세부 규격·권한·반영 지연은 첨부 PDF에 없으므로 NICEPAY의 별도 조회 문서를 확보해 어댑터를 정의한다. 조회 API가 준비되기 전에는 가맹점 관리자 거래 내역을 근거로 운영자가 확인하고 증빙·처리자를 남긴다.

복구 작업은 횟수와 지연을 제한하고 지속 실패 시 `manual_review`로 남긴다. 실패 항목을 삭제하거나 고객의 재결제로 덮지 않는다. `AuthToken`은 복구가 필요한 동안 암호화 저장하고 종료 후 보존 정책에 따라 제거한다. 키·토큰·원문 개인정보는 일반 로그에 남기지 않는다.

## 10. 예약 취소와 카드 환불

예약 취소와 카드 환불은 별도 결과다. 현재 홈페이지 관리자 취소, 수분양자 취소, PMS 전용 취소·판매일보 삭제 경로를 점검해 PG 주문을 가진 건은 모두 결제 서비스의 검사를 거치게 한다. 판매일보를 삭제해도 결제·환불 이력은 삭제하지 않는다.

관리자 화면은 승인액, 누적 환불액, 환불 가능 잔액, 이번 환불액, 취소 사유와 적용 규정을 먼저 표시한다. 취소 수수료 정책은 실제 운영 기준을 확정한 후 버전으로 저장한다. 현재 데모나 수분양자 박수 복원 규정을 일반 카드 환불 비율로 사용하지 않는다.

1. 서버가 주문을 잠그고 예약 취소 가능 여부와 환불액을 검증한다. 진행 중인 환불이 있으면 추가 환불을 막는다.
2. 유일한 취소 `Moid`와 환불 요청 키로 환불 작업을 저장한다.
3. PG 호출은 DB 트랜잭션 밖에서 수행한다. 전체 취소는 `PartialCancelCode=0`, 부분취소는 `1`을 사용한다.
4. 취소 응답 코드와 `Signature`, TID, MID, 취소 주문번호, 금액·잔액을 검증한다. PDF는 일반 취소 성공 코드를 `2001/2211`로 명시하므로 결제수단·취소 유형별 결과코드 정의를 확인해 적용한다.
5. 환불 성공을 저장하고 예약 취소·재고 해제·판매일보 정산을 진행한다. PG 환불 후 DB 반영이 실패하면 재환불하지 않고 동일 환불의 로컬 반영을 복구한다.

취소 결과가 불명확하면 `refund_pending` 또는 `manual_review`로 남기고 재고·예약 상태를 임의 완료 처리하지 않는다. 환불액 0원의 정책상 취소는 사유와 동의를 기록해 PG 호출 없이 예약을 취소할 수 있다. 숙박 유지 중 일부 금액만 환불하는 경우에는 재고를 해제하지 않는다.

부분취소는 승인 응답의 `CcPartCl`, 계약 MID와 사용 결제수단의 지원 여부를 확인한다. 전체 환불과 부분환불 이력을 합산해 중복·초과환불을 차단한다. 부분환불 정책이 확정되지 않으면 해당 기능을 운영자 확인 대상으로 두며, 이를 전체 취소로 임의 대체하지 않는다. [공식 승인 취소 문서](https://developers.nicepay.co.kr/docs/pg/auth/payment-cancel/)

테스트 MID에서 간편결제 부분취소는 PDF p.30의 제한을 따른다. 별도 허용 MID 없이 실제 부분취소 테스트를 진행하지 않는다. 일반 카드의 테스트 부분취소도 한도 복구와 전체취소 절차를 담당자에게 확인한다.

## 11. 고객 화면과 관리자 화면

| 화면 | 변경 내용 |
|---|---|
| 일반 예약 입력 | 서버 견적·할인 명세, 결제금액·취소 규정 동의, `결제하기` |
| 결제 진행 | 확보 만료시각, 결제창 재진입 안내, 중복 제출 차단 |
| 결과 화면 | 진행 중, 완료, 실패, 확인 필요를 서버 상태로 표시 |
| 일반 예약 조회 | 결제액·결제상태·호텔 확인상태·환불상태, 재시도 가능 여부 |
| 홈페이지 관리자 | 결제 필터, 승인·환불 이력, 결과 확인 대상, 환불 요청 |
| PMS 판매일보 | 결제 대기/완료 구분, NICEPAY 거래 연결, 임시 확보 만료, 취소 연계 |

`ApplicationCard`의 무조건적인 `현장 정산` 문구는 결제 방식에 따라 바꾼다. `registered`를 그대로 ‘결제 완료’로 번역하지 않는다. 호텔 확인은 별도 필드로 기록하고 알림톡 발송 성공 여부를 호텔 확인 상태로 사용하지 않는다. PG 접수 알림은 결제 완료 후 발송하며, 호텔 확정 알림은 호텔 확인 후 발송한다.

결제는 이루어졌으나 호텔 확인 전이라면 고객에게 그 상태를 명확히 표시한다. 운영자가 선결제 후 호텔 확인 방식 대신 호텔 확인 후 결제 링크를 원하면 결제 준비 시점을 호텔 확인 뒤로 이동할 수 있다. 그 경우 장시간 미결제 재고 점유와 링크 만료·재발급 정책을 별도로 정해야 한다.

| 홈페이지 | `src/app/reservation/payment/result/page.tsx` 신규 | 서버 상태 조회 기반 결과 화면 |
| 홈페이지 | `src/lib/seasonal-rate-table.ts`, `src/components/rate-guide.tsx` | 표시 요금과 서버 정책의 일치 |

| PMS | `application/website-booking/website-booking.service.ts` | 임시 확보·등록 분리, 기존 취소 경로의 결제 검사 |
| PMS | `application/website-payment/*` 신규 | NICEPAY 어댑터, 주문·승인·환불·복구·만료 서비스 |
| PMS | `domain/website-payment/*` 신규 | 주문·시도·환불·작업 엔티티 및 DB 제약 |

| PMS | `website-notification.service.ts` | 결제 완료/호텔 확인 이후 이벤트 처리 조건 |

Next.js 16.3.4의 로컬 Route Handler 문서를 기준으로 Node.js 런타임을 사용한다. PG 반환에 필요한 raw body 처리는 전용 Route Handler에 한정한다. 기존 예약 API의 JSON 전용 파서를 전역적으로 느슨하게 바꾸지 않는다.

## 13. 설정과 운영

| 설정 제안 | 위치와 용도 |
|---|---|
| `NICEPAY_ENABLED` | PMS. 신규 결제 준비 허용 여부. 꺼도 기존 반환·조회·환불·복구는 처리 |
| `NICEPAY_MID`, `NICEPAY_MERCHANT_KEY` | PMS 비밀 환경변수. 테스트·운영 분리 |
| `NICEPAY_ENVIRONMENT` | PMS. 주문·거래의 테스트/운영 구분 |
| `WEBSITE_PUBLIC_ORIGIN` | 서버 고정 HTTPS 사이트 주소. ReturnURL을 요청 Host에서 임의 생성하지 않음 |
| `PAYMENT_DATA_ENCRYPTION_KEY` | PMS. 복구용 토큰 암호화. 키 회전과 복호화 버전 관리 |
| `PAYMENT_HOLD_MINUTES` | PMS. 정책 확정 후 임시 확보시간 |

PG의 승인·취소 오류율, `approving` 장기 체류, `recovery_pending`, 환불 지연, 만료 미처리 확보를 운영 화면과 경보 대상으로 둔다. 주문번호·TID로 홈페이지/PMS/PG 내역을 추적할 수 있어야 한다. PG 가맹점 관리자와 로컬 승인·환불 잔액을 일 단위로 대조하고 수동 PG 취소도 차이를 확인한다.

최초 도입 시 기존 현장결제 예약을 자동 PG 주문으로 전환하지 않는다. 신규 일반 예약부터 기능 플래그로 적용한다. 배포 롤백은 신규 결제만 중지하고 진행 중인 거래의 반환·복구·환불 기능은 유지한다. 실제 배포와 운영 DB 적용은 사용자가 수행한다.

## 14. 검증과 완료 기준

실결제 전에 PG 대역 테스트와 별도 PostgreSQL 통합 테스트를 수행한다. 실제 결제 테스트는 계약 MID·담당자 안내 범위에서 진행한다.

| 검증 | 완료 기준 |
|---|---|
| 가격 | 11개 객실, 시즌·공휴일·다실·연박·부가서비스의 화면 견적과 주문·PG 금액 일치 |
| 위변조 | 금액·MID·Moid·TID·서명·반환 토큰 변경과 다른 주문 재사용 차단 |
| 인코딩 | 한글 이름·사유·40 byte 상품명, EUC-KR/UTF-8 반환 처리 확인 |
| 중복 | 이중 클릭·반환 재전송·새로고침·다중 작업 처리기에서 승인·등록·환불 1회 |
| 재고 | 마지막 객실 경합, 다실 중 일부 실패, 만료와 승인 경합에서 초과 판매 없음 |
| 장애 | 승인 직전/직후 프로세스 종료, 응답 유실, DB 장애, 망취소 실패를 복구 가능 |
| 환불 | 전액·부분·누적·초과·동시환불, PG 취소 성공 후 DB 실패 처리 검증 |
| 권한 | 비회원 타 주문 조회, 관리자 세션 만료, 위조 Origin, 임의 승인 URL 차단 |
| 모바일 | iOS Safari·Android Chrome·카카오 인앱에서 카드 앱 왕복과 결과 복귀 확인 |
| 운영 | 미결제 확정·알림 방지, 수동 PMS 삭제·취소 경로, 알림 실패 시 결제 유지 |

외부 PG 호출 중 DB 잠금이 장기간 유지되지 않는지, 결제 처리기가 재시작 후 누락 작업을 회수하는지도 확인한다. 성공 건뿐 아니라 실패·결과 불명확 건을 운영자가 찾고 처리할 수 있어야 공개 가능하다.

## 15. 구현 순서와 확정할 사항

1. **요금과 정책 정리:** 서버 할인 계산, 시즌 공백, 취소 규정, 선결제와 호텔 확인 순서를 확정한다.
2. **관리자 설정 선행 구현:** PMS DB 기반 요금 관리·방막기, 홈페이지 설정 화면, 공개 요금·예약 견적 일치와 직접 API 차단을 먼저 구현한다. 이후 결제 테이블·재고 확보·상태·중복 방지·복구 작업을 추가한다.
3. **카드 인증과 승인:** 공식 결제창, 서명·인코딩, PC/모바일 반환을 연결한다.
4. **조회와 환불:** 고객 조회, 관리자 환불, 모든 PMS 취소 진입점과 정산을 연결한다.
5. **장애 검증과 공개 준비:** 테스트 MID 검증, 운영 MID 설정, 제한 공개 및 거래 대조를 진행한다.

| 확정 항목 | 제안 또는 필요한 답 |
|---|---|
| 첫 적용 대상 | 일반 예약 전액 카드결제부터 시작 |
| 결제 시점 | 재고 임시 확보 후 선결제, 호텔 확인 별도 |
| MID 계약 | 인증결제 v2.1.3 규격, 허용 결제수단·간편결제·부분취소 여부 |
| 할인 | 비수기 1실·1박 5,000원, 금·토 및 시즌 경계 적용 확정 |
| 재고 확보 | 15분 제안, NICEPAY 인증 유효시간 확인 후 조정 |
| 일반 예약 취소 | 날짜별 수수료·노쇼·호텔 사정 취소·부분환불 정책 |
| 결과 조회 | NICEPAY 거래 조회 API 규격·권한·정합성 확인 방식 확보 |
| 수분양자 | 무료/현장 정산 유지, 유료 추가분 온라인 결제는 후속 범위 |
| 가상계좌 | 입금 통보·만료·환불 별도 설계 후 추가. 계좌 발급 성공을 결제 완료로 처리하지 않음 |

이 문서 작성 범위는 설계와 코드 조사다. PG 키 설정, 실제 결제·환불, 애플리케이션 기능 변경, DB 적용 및 배포는 수행하지 않았다.
